# Changelog

All notable changes to zvidlib will be documented in this file.

## Unreleased

- The native HEVC encoder's §8.7.3 SAO search now considers band offset (`SaoTypeIdx == 1`) alongside the four §8.7.3.2 edge-offset classes. `engine/encoder/recon.rs::estimate_sao` evaluates all 32 `sao_band_position` candidates per component — each band's four consecutive bands taking their own mean error, clamped to the §7.4.9.3 signalable magnitude and signalled with a `sao_offset_sign` each — and scores them against the edge classes and against leaving SAO off under one `D + lambda * R` comparison, so the type is chosen by what it buys net of the four sign bins and five position bins it costs. The §7.4.9.3 chroma inference still holds: Cb and Cr share one type, each carrying its own offsets and, under band offset, its own `sao_band_position`. Band offset reaches the error edge offset cannot — a CTB biased over a *value range* rather than around a local edge — and the writer's §7.3.8.3 band path, previously never exercised, now reaches the bitstream. Measured on the same QP 12–51 sweep over both test pictures, against the same writer with SAO off: the noise-carrying picture gains two operating points the edge-only search left on the table, +0.14 dB for +0.5% of slice at 64x48 and +0.15 dB for +0.2% at 128x96 at QP 12 (against +0.04 dB before), and +0.09 dB for +0.6% and +0.13 dB for +0.2% at QP 20 (against nothing before). Band offset is never selected on the smooth picture at any QP — that content's error is edge-shaped — where the only change is a byte off the slice from the type now being decided on rate-distortion rather than on gain alone; two coarse noise points give back 0.001 to 0.003 dB for two to three bytes for the same reason.
- Re-take the HEVC engine's x86_64 SSE4.1 and AVX2 kernel ratios on an Intel host, so the `hevc::engine::simd` per-kernel table no longer speaks for x86_64 from one vendor's readings. The figures #215 recorded all came from an AMD EPYC-class `ubuntu-latest` runner; the same two `#[ignore]`d stage benchmarks have now been run on an Intel Coffee Lake host (`macos-15-intel`, i7-8700B, `sse4_1` + `avx2`, no AVX-512), three runs of best-of-five-interleaved-rounds each, against a same-day AMD control run so the two are compared on the same code. The question the ticket asked - whether the §8.5.3.3.4 `combine_weighted` SSE4.1 kernel, which measured 0.95x of scalar on Zen and is therefore dispatched to the scalar reference, lands on the other side of 1.00x on an Intel core whose `pmulld` behaves differently - is answered no: with the kernel temporarily restored so it could be timed, it read 1.00x in the block path and 0.75x over an L1-resident buffer on Coffee Lake, further below scalar than on Zen rather than above it. That dispatch is confirmed across both vendors and is unchanged, as is every other dispatch decision: no kernel changes which side of 1.00x it is on between the two. What does differ is magnitude, and the table now carries both vendors side by side rather than one: Intel reads materially lower on everything bounded by vector width (§8.7.3 SAO 2.7-3.0x against 4.6-7.4x, AVX2 `filter_taps` over a buffer 1.7-1.8x against 2.5-2.7x, two-dimensional 8-tap luma 1.6-1.9x against 2.1-2.7x) and slightly higher on §8.7.2 deblocking, which is bounded by edge shape instead. The one kernel whose *sign* is vendor-dependent is the AVX2 `combine_weighted`: 1.4x in the block path and 2.0-2.2x on a bare buffer on Zen, but 0.93-0.95x and 0.92-0.93x on Coffee Lake, where a 256-bit `vpmulld` is two uops against the four-lane `pmulld` LLVM auto-vectorizes the scalar loop into. It stays dispatched to unconditionally - the AMD win is large, the Intel cost is a few percent of one kernel, and splitting on a CPUID vendor check would add a second dispatch arm to keep bit-exact for it - and both the module table and the dispatch site now say so rather than leaving the AMD figure to stand for x86_64. No dispatch, kernel or decoded output changes; this is the measurement and what it is recorded against.
- Vectorize the HEVC decoder's 8-bit 4:2:0 YUV-to-RGBA output conversion, which was the largest single stage in a whole-frame decode and the only large one with no vector kernel at all. `picture_to_rgba` applied the fixed BT.601/709 limited-range integer matrix one sample at a time, and the issue #189 stage attribution measured it at a third of everything the whole-frame benchmark groups time - on the path of both `hevc_decode_1080p` and `hevc_decode/<isa>`, so every whole-frame SIMD number the suite reported was diluted by roughly a third for a stage no HEVC kernel touched. The conversion now lives in `src/hevc/color_convert.rs` with SSE4.1, AVX2 and NEON backends beside the scalar reference, dispatched through `zvidlib::simd` like every other kernel family in the crate: `simd::set_override` reaches it and `simd::active_by_site` reports it as `hevc_color_convert`. Each backend computes four (SSE4.1, NEON) or eight (AVX2) pixels at a time in `i32` lanes and writes each pixel's four components as one little-endian `R | G<<8 | B<<16 | 0xFF00_0000` word, so the RGBA interleave costs two shifts and two ORs rather than a byte-level pack, and each row's tail runs the scalar reference. Every backend is bit-exact with that reference - the arithmetic is `i32` throughout in the same order with the same arithmetic `>> 16`, a decoded 8-bit picture's samples are clipped to `0..=255` so no product can reach the scalar path's saturation, and a new test checks all of it across widths that leave a tail for both vector widths and across both chroma column parities. Decoded output is therefore unchanged bit-for-bit. Measured on 48 frames of the bundled 1920x1080 sample on Apple Silicon, `--release`, colour conversion falls from 9.86 ms/frame to 1.98 ms/frame (5.0x) and the whole-frame decode from 30.20 ms/frame to 21.39 ms/frame, moving the `scalar`-to-`neon` whole-frame ratio from the ~1.06x that prompted issue #189 to 1.41x. A new per-ISA `hevc_color_convert` criterion group in `benches/hevc_decode.rs` times the stage under the same bit-exactness and per-site override guards as the other `hevc_*` groups, the `Stage::ColorConvert` profiler classification now counts as vectorized, and the breakdown in `benches/README.md` is re-measured with both arms reported side by side.
- `AacSampleReader::get_range` no longer throws away its decoded-packet cache every time a read advances. `ensure_decoded` treated `decoded` as all-or-nothing: any packet missing from the requested window reset the decoder, cleared the map, and re-decoded the window plus `preroll_packets`. Forward playback, which shares almost every packet with the read before it, therefore cost the same per request as a cold seek - about 100 us against about 1.5 us for a range already resident. The reader now tracks the contiguous run of packets the decoder has produced and, when a request starts inside that run or immediately after it, decodes only the access units past its end with no reset and no preroll; cold, backwards, and gapped requests keep the reset-plus-preroll path a real seek needs. Retained packets are bounded by the `Limits` knobs that already govern a decode - at most `max_decode_samples_per_seek` packets holding at most `max_allocation_bytes` of samples - with the packets furthest behind the request evicted first, and the per-read copy now visits only the buffers that overlap the request rather than the whole cache. Measured on an Apple Silicon host with the two bench binaries interleaved, `aac_reader_sequential/forward_walk_stereo_48k` goes from about 300 us to about 28 us per request, which takes a forward read from more expensive than a cold seek to roughly 3x cheaper than one, and `aac_reader_seek/random_seek_preroll_stereo_48k` does not regress. Decoded output is unchanged.

- The native HEVC encoder's lossy residual writer now runs the ITU-T H.265 §8.7.3 sample adaptive offset filter behind the §8.7.2 deblocking pass, in the §8.7.1 order. `engine/encoder/lossy.rs` emits `sample_adaptive_offset_enabled_flag == 1` in the SPS and the `slice_sao_luma_flag` / `slice_sao_chroma_flag` pair in the slice header, and codes the §7.3.8.3 `sao( )` structure per CTB — merge flags, `sao_type_idx`, `sao_offset_abs`, `sao_offset_sign`, `sao_band_position` and `sao_eo_class` — with the §9.3.3 binarizations and §9.3.4.2 contexts the decoder already parses. The parameters come from `engine/encoder/recon.rs::estimate_sao`, which was already there and unused by this writer; it now decides the two chroma components together on one shared class, because §7.4.9.3 infers `SaoTypeIdx[2]` and `SaoEoClass[2]` from cIdx 1 and a Cb and a Cr that picked different classes are not a bitstream. What `write_idr_residual_slice` returns is therefore still exactly what a conforming decoder reconstructs, sample for sample, at every QP, on both the smooth and the noise-carrying test picture.

  SAO is on, and the writer turns it off per slice when it does not pay. Unlike deblocking, which is signalled once in the PPS, SAO costs a `sao( )` structure on every CTB including every CTB it does nothing to, so the decision is taken twice against the same `D + lambda * R` the mode search uses: per CTB a class is signalled only when the squared error it removes clears the bins it would be coded with, and per slice the whole pass is kept only when the error it actually removed clears the bins the whole grid would be coded with. When it does not, the reconstruction reverts to the deblocked one and both slice flags go out as 0, which §7.3.8.3 reads as "code nothing" and leaves the cost at the two header bits. Measured against the same writer with SAO off, at the same QP with the same mode decisions, in whole-picture PSNR and slice bytes over a QP 12 to 51 sweep on both test pictures: on smooth content at QP 12 the pass is taken and buys +0.73 dB for +11.4% of the slice at 64x48 and +0.89 dB for +13.4% at 128x96; on the noise-carrying picture it is taken at QP 32 and 37 and buys +0.22 to +0.35 dB for +3.5% to +7.5%. At every other point of the sweep the slice-level test declines it and the slice is the deblocked writer's to the byte, or within one byte of it. Against the SAO-off writer's own rate-distortion curve, interpolated in log-rate at the same slice size, the two clear wins sit 0.38 and 0.43 dB above it; the two accepted noise points at QP 32 sit 0.08 and 0.14 dB below it, which is the fixed lambda being a heuristic rather than SAO being a loss, and is tracked separately.

  The coding loop is now two passes over the picture rather than one, because §7.3.8.3 puts a CTB's SAO parameters at the head of that CTB's slice data while §8.7.1 only lets them be searched once the whole picture is coded and deblocked: a decision pass searches every coding unit and builds the reconstruction, the filters run, and a bitstream pass codes the recorded decisions with the `sao( )` syntax in front of each. Nothing a decision depends on changes in between — §8.4.4.2.2 intra prediction reads the unfiltered reconstruction, which the decision pass has already built — so the picture that is coded is exactly the picture that was searched, and no coding unit is searched twice.

- Bound the HEVC encoder's `BitWriter::ue`/`se` to the §9.2 `codeNum` cap of `2^32 - 2`, the same cap `BitReader::ue` already enforces with `ExpGolombOverflow`. `ue(u32::MAX)` computed `codeNum + 1 == 2^32` and emitted a 33-bit codeword with a 32-zero prefix - outside the range §9.2 defines and outside what this crate's own reader, or any conforming decoder, reads back - and `se(i32::MIN)` mapped to `2 * 2^31`, which overflowed the `u32` `codeNum` and so wrapped to `0` in release builds, silently writing the wrong value. Both now assert their documented bound (`BitWriter::MAX_UE`, `BitWriter::MIN_SE`/`MAX_SE`) instead, because reaching it is a caller computing a syntax element wrongly rather than bad input data: every `ue(v)` field the HEVC writers emit - parameter-set ids, picture dimensions, reference-list counts - is bounded far below the cap, so no shipped caller's bits move. With `codeNum + 1` now guaranteed to fit `u32`, the 33-bit special case `ue` carried disappears and the codeword is one `put_bits` pair again. Tests pin the boundary in both directions - `2^32 - 2` emits the bit-at-a-time reference codeword and round-trips through `BitReader::ue`, the codeword one past it is what the reader rejects, and `u32::MAX`/`i32::MIN` panic - alongside `se`'s own extremes at `i32::MIN + 1` and `i32::MAX`.

- The native HEVC encoder's lossy residual writer now runs the ITU-T H.265 §8.7.2 in-loop deblocking filter. `engine/encoder/lossy.rs` emits `pps_deblocking_filter_disabled_flag == 0` in the PPS (plus the `slice_loop_filter_across_slices_enabled_flag` §7.3.6.1 requires alongside it), and `engine/encoder/recon.rs` gains `deblock_reconstruction`, which drives the decoder's own §8.7.2 kernels over the writer's reconstruction rather than carrying a second implementation of the filter. The filter runs as one whole-picture pass after the last coding unit is coded, not interleaved into coding order, because §8.4.4.2.2 intra prediction reads its neighbouring samples *prior to* the in-loop filter process - the filtered samples are the picture's output, never this picture's own prediction input. What the writer returns is therefore still exactly what a conforming decoder reconstructs, sample for sample, at every QP. Measured against the same writer with the filter off, on the same picture at the same QP, whole-picture PSNR improves by 0.55 to 0.95 dB on smooth 64x48 content (luma 0.39 dB at QP 20, 0.56 dB at QP 26, 0.85 dB at QP 32, 1.01 dB at QP 44) and by up to 1.16 dB at 128x96. On content carrying per-sample noise the §8.7.2.5.3 `d < β` decision correctly declines most edges and the gain falls to 0.01 to 0.29 dB, which is the filter behaving as specified rather than a shortfall. §8.7.3 SAO stays off: it is a per-CTB parameter search plus §7.3.8.3 slice-data syntax, a decision independent of deblocking, and it is tracked separately.

- Recover almost all of what the AV1 encoder's transform-size gain correction cost. That correction keeps the fast size search fair to the smaller transforms by probing one block of a size trial with the whole transform-type set and extrapolating the measured gain over the trial's remaining blocks, and it was paid on every trial of every coding block, whether or not the ranking was ever in doubt. What a probe measures, though, is a ratio between the whole set's cost and DCT's on the same block, and that ratio is a property of the frame's content and its quantizer far more than of the individual block - so it is now measured on a sample of the size searches, one coding block in two, and the blocks in between are corrected by what the frame has already measured at each transform size. The sample is taken per *coding block* rather than per size trial because a block ranks its sizes against each other: correcting one of its trials from a fresh probe and another from a remembered ratio compares two different estimators, and doing that made `TX_4X4` unselectable on the 96x80 test pattern again. A block whose search does probe still uses its own measurement, exactly as every block did before, so sampling every block reproduces the previous encoder bit for bit. Transform-type candidate evaluations on a 640x352 frame fall from 22,837 to 16,065 at `base_q_idx = 32` and from 20,462 to 14,551 at 160, against 14,921 and 13,606 for the same search with the correction removed entirely - 86% of the correction's evaluations at both quantizers, and the frame's coded bytes are identical in all three. In wall-clock terms, from the minimum of eight interleaved rounds per arm of `av1_encode_frame_q{32,160}` at 640x352 on a contended Apple Silicon host, running the shipped search, the previous one, and a correction-free build in the same session: 201/145 ms scalar/neon at q32 and 170/123 ms at q160, against the previous 223/158 ms and 215/151 ms - 1.09-1.26x - and against 194/147 ms and 166/127 ms with no correction at all, which the sampled search is at or inside the noise of in all four groups. The search's own bounds are unchanged and still enforced: `the_search_shortcuts_stay_within_their_rate_and_distortion_bound` holds at 0.05 dB and 1.5%, `non_lossless_frames_round_trip_within_a_distortion_bound` still finds every signallable transform size selected by the shipped search, and `TX_4X4` is still selected on the 96x80 pattern. The emitted bitstream does change on that pattern, so the digests `a_fixed_frame_encodes_to_the_same_bytes_on_every_host` pins are regenerated; lossless (`base_q_idx = 0`) searches nothing and is untouched. The candidate counts and wall-clock figures above were taken at the sampling interval of eight the correction first shipped with, which was chosen on the 96x80 test pattern alone. That interval has since been calibrated against the same estimator probing every size search, on six 192x160 frames whose statistics differ from that pattern - a hard scene edge, four unrelated quadrants, full-range noise, a smooth surface, directional edges, and the pattern itself - and moved from eight to two. Costed in the encoder's own `sse + lambda * bits` at equal quantizer, the worst frame's penalty against the unsampled estimator falls from +78.7% at eight to +44.1% at two, and the mean penalty against the exhaustive search from +1.97% to +1.05%; two spends 155,143 transform-type candidate evaluations across that set against eight's 136,250 and the exhaustive search's 700,004, so the four-fold reduction the shortcuts exist for still holds - at one it would not, with 181,557 - and 7% more encode time. Every worst case is the same frame at the same quantizer, a scene edge whose halves have unrelated statistics, and what is left at two is the estimator mixing regions rather than the sampling rate. The 96x80 pattern cannot see any of this - every interval from one to sixteen lands within 0.03% of the unsampled estimator on it - so `the_type_gain_sampling_interval_holds_on_content_it_was_not_tuned_on` measures the varied set at 128x96 against per-frame ceilings the previous interval of eight exceeds on three of them. That remaining regional error is now addressed as well: the per-size gain a probe measures is a property of the content around the block it was measured on, so accumulating every probe of a size equally over the whole frame lets the far side of a scene edge outvote a block's own neighbourhood, and no sampling interval can undo that. Each accumulator is therefore aged by `(n-1)/n` before a new probe joins it, so a probe's weight decays geometrically over the following `n` and - since the size searches that probe are visited in the decoder's superblock raster order - the ratio a block reads back is the one measured around it, following the content across a region boundary within a few coding blocks instead of never. The window is four, chosen over a per-superblock-row reset (too coarse on a small frame, and it drops the correction entirely at the start of each band) and over a per-region ratio (which needs a region map the encoder does not have) by measuring each frame's worst penalty at both 128x96 and 192x160 over the six quantizers: at 192x160 the scene edge falls from +44.1% against the unsampled estimator to +9.3%, and at 128x96 from +30.0% to +2.1%, while `quadrants`, `smooth`, `noise`, `diagonals` and the pattern itself all stay exactly where the frame-wide accumulation left them. Shorter windows start trading that back - two costs `quadrants` +1.5% and one, which remembers only the last probe, costs the pattern +3.1%, a single probe being too noisy to rank a size on - and longer ones give the improvement up, +16.4% at eight and +30.0% at thirty-two. The correction stays cheap: 155,392 transform-type candidate evaluations against the frame-wide accumulation's 155,143, 0.16% more against the exhaustive search's 700,004, and 0.971 s against 0.954 s over that set from the minimum of five interleaved rounds per window, +1.8%. `the_type_gain_sampling_interval_holds_on_content_it_was_not_tuned_on` takes the scene edge's ceiling from 40% to 4% accordingly; the other five frames' ceilings, the 0.05 dB / 1.5% shortcut bound, the size coverage in `non_lossless_frames_round_trip_within_a_distortion_bound` and `TX_4X4` selection on the 96x80 pattern are all unchanged and still hold.
- Widen the HEVC encoder's RBSP bit writer and give byte-aligned PCM sample data a path that bypasses the bit accumulator entirely, which makes writing a lossless access unit roughly 23x faster and the raw syntax writer roughly 5.9x faster. `BitWriter::put_bits` walked its field one bit at a time through `put_bit`, so every fixed-length `u(n)` field cost `n` read-modify-write passes over the same trailing byte and a 32-bit field cost 32 of them; it now writes a chunk at a time - whatever fills the trailing partial byte, then whole bytes appended directly, then the remainder as a new partial byte - and `ue(v)` routes its codeword suffix through that path instead of its own bit loop (which every codeword the §9.2 `codeNum` cap permits now fits, so the suffix needs no splitting). `align_zero` stopped writing padding bits at all: partial bytes are pushed zeroed and only ever ORed into, so the padding is already zero and only the bit counter has to move. The second win is the larger one and is not a widening but a bypass - a new `BitWriter::put_bytes` extends the output buffer directly when the writer is already byte-aligned, and §7.3.8.7 `pcm_sample[]` data always is, because `pcm_alignment_zero_bit` immediately precedes it, so a PCM CTB's 16-byte luma rows and 8-byte chroma rows are now a bulk copy rather than 384 trips through the accumulator. Unaligned callers of `put_bytes` still get correct MSB-first packing. This changes throughput and never bits: `tests/hevc_bitstream_byte_identity.rs` pins whole PCM access units at three picture sizes and the raw syntax stream to digests captured from the pre-rewrite writer, and unit tests check the widened `put_bits` against the bit-at-a-time reference it replaced at every field width from 0 to 32 crossed with every starting bit offset, `put_bytes` against the per-byte path aligned and unaligned, and the zero-fill `align_zero` no longer performs. Measured on a contended Apple Silicon host as the best of seven interleaved rounds per arm: `hevc_encode_bitwriter` 3.43 ms -> 0.58 ms and `hevc_encode_640x352_pcm_write` 8.32 ms -> 0.35 ms. Both groups still read identically under every instruction set, which is the expected result rather than a null one - a widening rewrite adds no `simd::active_by_site()` dispatch site, so there is no SIMD axis for it to move on, and `benches/README.md`'s "Where the SIMD axis reads flat" section now says so explicitly and records the scalar speedup separately so a flat SIMD arm is not read as no work having been done.

- Settle whether the HEVC encoder's §9.3.5 CABAC bypass bins are cheaper coded a run at a time than a bin at a time, and record in `benches/README.md` that they are not, correcting the 1.73x that section previously predicted for the change. §9.3.5.5 unrolled over `n` bins is `ivlLow = ( ivlLow << n ) + ivlCurrRange * value` followed by the same carry-controlled emission of the top `n` bits, and that part holds exactly: implemented against the bin-at-a-time engine it is byte-identical and leaves an identical `ivlLow` and `bitsOutstanding` for every run length from 1 to 32 from every primed engine state, and the lossy residual writer's bytes do not move at any QP. It is simply not faster - measured as the best of 25 rounds of the two paths interleaved in one process on an Apple Silicon host, the ratio is 0.91x at a run length of 2, 0.90x at 4, 1.06x at 8, 0.98x at 16 and 0.95x over a mixed 1-16 workload, straddling 1.00 without ever leaving the noise, and batching a whole run's resolved bits into one byte-at-a-time `BitWriter::put_bits` did not move it either. What a bypass bin costs is the three-way, data-dependent Figure 9-13 decision - emit a bit, emit a carry-resolving bit, or defer one - which the unrolled step still runs once per bin, plus the `put_bit`-at-a-time sink underneath it, so the encoder is unchanged and the reachable headroom is in the bit sink. `benches/hevc_encode.rs` gains the `hevc_encode_cabac_bypass` group and `zvidlib::hevc_encoder_bench::cabac_encode_bypass_runs` behind it, measuring the §9.3.5 encoder over contiguous bypass runs of 1 to 16 bins rather than the single interleaved bins `hevc_encode_cabac` codes - the shape 62% of the lossy residual writer's 1,472,210 bins per access unit actually have, and the group any future attempt at this has to move - run once per instruction set under the same bit-exactness and `active_by_site()` guards as every other per-ISA group, and expected to read flat across them because nothing here is vectorized.
- Add `criterion_baseline.py variance`, which reads the per-group run-to-run spread off a series of stored `main` baselines: for each consecutive pair it takes every benchmark's absolute median delta -- the same quantity the delta report thresholds -- and reports each group's median, p95, worst observation, and the smallest whole 5% step that clears that worst observation. Per group rather than one number for the suite, because a whole-frame 1080p group and a microbenchmark do not share a noise floor and a single global threshold may be the wrong shape for both. Arms that appear or disappear between runs are listed separately instead of being folded in, since a runner pool that stopped offering AVX2 is not a percentage, and a group that does it cannot be gated on at any threshold; the report names the groups whose entire spread fits under a candidate gate, which is the precondition `--fail-on-regression` has been waiting on. Samples below ten pairs mark themselves provisional, because a p95 read off a handful of observations is just the worst thing seen so far. The 15% threshold is unchanged and still uncalibrated: the timed job that stores baselines landed alongside the delta report, so no run of consecutive `main` baselines exists to calibrate against yet, and `benches/README.md` now says so plainly and documents the one command that does the calibration once they accumulate.
- Run the criterion benchmark suite in CI, with stored baselines and a per-group delta report. `cargo bench --benches --no-run` now runs on every pull request across all seven bench targets: one build, no measurement, guarding against the way benchmark suites usually die - the bench code stops compiling against the crate and nobody notices for months. Timed runs happen only on `main` pushes and `workflow_dispatch`, because GitHub's shared runners vary between two runs of the same commit by far more than the regressions worth catching, and a PR check that fails on noise gets disabled rather than fixed. Each timed run measures the full suite -- every `[[bench]]` target, not one of them, since naming a single target would let the other six rot unnoticed -- including the opt-in 1080p groups, reduces `target/criterion/` to one small JSON baseline, and diffs it against the newest baseline artifact from a previous `main` run, writing a per-group table of criterion's median point estimate to the job summary. Anything past a deliberately loose 15% threshold is flagged there rather than failing the job: the suite's real run-to-run variance on the runner pool is not known yet, and a threshold guessed tighter than the noise floor produces false regressions immediately. The job also lifts `zvidlib::simd::available()`, the widest detected instruction set, and `active_by_site()` into its summary, which every bench target now prints before timing anything through the shared `log_host_isas` group - `bench_across_isas` runs one arm per available instruction set, so on a runner without AVX2 the `avx2` arm is absent rather than silently reporting scalar numbers under a vector label, and an arm that vanished because the runner pool changed otherwise looks identical to one that never existed. `benches/README.md` gains a committed baseline table of scalar versus each instruction set, per group and per codec, with the measuring host's CPU named, since a benchmark number without a stated CPU is not comparable to anything. That table is generated by the same script rather than hand-typed (`criterion_baseline.py table`), from the elementwise minimum across several rounds -- contention only ever makes a measurement slower, so the fastest observation of an arm is the closest any round got to an uncontended one. On an Apple M1 it puts 53 groups on the record, from the AV1 forward 4x4 DCT at 6.46x over its scalar arm down to a handful of arms sitting at or just below parity. The table is stamped with the commit it was measured at, because kernels land often enough that a table without one cannot be told from a stale one. Committing it also settled a question a one-off measurement would have gotten wrong: three independent measurement sets put `hevc_intra_pred` at 0.62x, then 1.04x, then 1.09x of its scalar arm with the kernel unchanged, and `av1_intra_paeth` and `av1_forward_dct_32x32` walked from 0.78x to 0.98x and 0.95x the same way -- what moved was the load average on the measuring host, not the code. On this host no arm is reliably below parity except the ones with no vector kernel at all, and the near-parity rest is the auto-vectorization story this crate already documents. That is also why the CI threshold is loose, compares medians rather than means, and reports rather than fails: a shared runner is a noisier host than this one, not a quieter one.
- Cut the AV1 encoder's non-lossless per-frame cost by 2.5-2.9x at `base_q_idx = 32` and 3.9-5.6x at `base_q_idx = 160`, by taking three pieces of work out of the mode/size/type search that the search's own cost function shows cannot change its answer, and one that changes it only marginally. The search minimizes `sse + lambda * bits` over partitions, transform sizes and transform types, and `benches/av1_encode.rs` now has whole-frame `av1_encode_frame_q{0,32,160}` groups (640x352 by default, 1920x1080 behind `ZVIDLIB_BENCH_LARGE=1`) that measure it end to end rather than by inspection, alongside the existing forward-transform kernel groups. What they show is that the cost is candidate *count*, not per-candidate work: a 640x352 frame at `base_q_idx = 32` evaluated 158,965 transform-type candidates - a forward transform, quantize, dequantize, inverse transform and rate estimate each - for a frame that finally writes a few thousand blocks. First, the partition and transform-size decisions were recomputed once per level of the partition tree: `decide_split` trial-codes the whole block and all four subtrees, and then the emitting pass ran the identical search again from the identical state, at every level. Both decisions are now memoized per `(block size, MI position)`, which is exact - a block is only ever searched from one encoder state per frame, because every trial rolls the state back with the same snapshot the emitting pass then replays from - and it alone leaves the output bit-for-bit identical. Second, a block whose residual energy plus the one `all_zero` bit already costs less than the cheapest block that codes any coefficient at all (`sse + lambda < 7 * lambda`) is now written as an all-zero block without running a single transform, which is a consequence of the cost function rather than an approximation of it, and is most of a flat picture. Third, `decide_split` returns early when the unsplit cost is already at or below the header charge a split would pay, since a subtree cost is a sum of squared errors and positive bit counts and so can never be negative. Fourth and last, the trials that rank *sizes* and *partitions* now score each block on the transform set's DCT alone instead of on all five types of `TX_SET_INTRA_2`; the type each block finally writes is still chosen by the full search on the emitting pass. That fourth one is the only approximation, and it is bounded: candidate evaluations fall about 10.6x (158,965 to 14,921 at 640x352, `base_q_idx = 32`), the stream is byte-for-byte unchanged at `base_q_idx` 1, 8, 32, 80 and 160 on that frame and 1.2% *smaller* at 200, and on the smaller 96x80 pattern the worst case across those quantizers is 0.8% more bytes reconstructing 0.13 dB better. The one behavioural change is that the shipped search no longer selects `TX_4X4`, whose wins came from exactly the per-block type search the trials no longer run; the emitting path is unchanged and still writes every signallable size, which is now asserted against the exhaustive search the shortcut stands in for. Lossless (`base_q_idx = 0`) is untouched: it searches nothing, its code path is unchanged, and its output is unchanged. The speedups above are the minimum of three interleaved runs per arm of `av1_encode_frame_q{32,160}` at 640x352 on an Apple Silicon host under concurrent load (base 952/533 ms scalar/neon at q32 and 1357/667 ms at q160, against 334/212 ms and 243/173 ms); a single run on that host is worth several times its own value in noise, so the ratios come from the interleaved minimums rather than from one pass.

- Add the half-identity `V_*`/`H_*` inverse transform kernels, so every entry of every AV1 transform set is now decodable. `Tx1d` gains an `Identity` kernel and `Av1TxType` gains `V_DCT`, `H_DCT`, `V_ADST`, `H_ADST`, `V_FLIPADST` and `H_FLIPADST`; `inverse_transform` runs the identity along the axis the type names and the DCT or ADST butterfly along the other, with the flip where the type calls for one. Until now those types decoded correctly out of `get_tx_set`/`read_tx_type` but had no kernel and were rejected as `Unsupported`, which left `TX_SET_INTRA_1` (4x4/8x8 intra), `TX_SET_INTER_2` (16x16 inter) and especially `TX_SET_INTER_1` (4x4/8x8 inter, ten of whose sixteen entries were unimplemented) only partly decodable, so a conforming stream that picked one failed to decode. The identity pass carries AV1's own identity scale, `sqrt(N / 2)` in the same 14-bit fixed point the butterflies multiply in, because it shares a block with a butterfly pass whose gain it has to match - without it a half-identity block would reconstruct two to four times too small. The 2-D `IDTX` type runs that same scaled identity on both axes and takes the same `transform_shift` as every other type, so it reconstructs at the magnitude a conforming decoder produces rather than at the raw dequantized one, and it dispatches to the vector kernels like the rest instead of taking a short path around them; only the ADST passes still fall back to the DCT above `TX_16X16`, since the identity is defined at every size. The encoder-side `forward_transform` applies the same scale, so a round trip through a half-identity type cancels exactly as it does for the others, and the SSE4.1/AVX2/NEON kernels cover the new types bit-exactly against the scalar path rather than falling back to it. New coverage decodes a bitstream signalling each new type - `V_DCT`/`H_DCT` from `TX_SET_INTRA_1` and `TX_SET_INTER_2`, and all sixteen `TX_SET_INTER_1` entries from an 8x8 inter transform block under `TX_MODE_SELECT` - and checks each reconstructs bit-exactly through the matching kernel and distinguishably from every other type. Decoded output for the checked-in AV1 elementary streams is unchanged: they signal no `tx_type` symbol.
