# Changelog

All notable changes to zvidlib will be documented in this file.

## Unreleased

- Vectorize the HEVC decoder's 8-bit 4:2:0 YUV-to-RGBA output conversion, which was the largest single stage in a whole-frame decode and the only large one with no vector kernel at all. `picture_to_rgba` applied the fixed BT.601/709 limited-range integer matrix one sample at a time, and the issue #189 stage attribution measured it at a third of everything the whole-frame benchmark groups time - on the path of both `hevc_decode_1080p` and `hevc_decode/<isa>`, so every whole-frame SIMD number the suite reported was diluted by roughly a third for a stage no HEVC kernel touched. The conversion now lives in `src/hevc/color_convert.rs` with SSE4.1, AVX2 and NEON backends beside the scalar reference, dispatched through `zvidlib::simd` like every other kernel family in the crate: `simd::set_override` reaches it and `simd::active_by_site` reports it as `hevc_color_convert`. Each backend computes four (SSE4.1, NEON) or eight (AVX2) pixels at a time in `i32` lanes and writes each pixel's four components as one little-endian `R | G<<8 | B<<16 | 0xFF00_0000` word, so the RGBA interleave costs two shifts and two ORs rather than a byte-level pack, and each row's tail runs the scalar reference. Every backend is bit-exact with that reference - the arithmetic is `i32` throughout in the same order with the same arithmetic `>> 16`, a decoded 8-bit picture's samples are clipped to `0..=255` so no product can reach the scalar path's saturation, and a new test checks all of it across widths that leave a tail for both vector widths and across both chroma column parities. Decoded output is therefore unchanged bit-for-bit. Measured on 48 frames of the bundled 1920x1080 sample on Apple Silicon, `--release`, colour conversion falls from 9.86 ms/frame to 1.98 ms/frame (5.0x) and the whole-frame decode from 30.20 ms/frame to 21.39 ms/frame, moving the `scalar`-to-`neon` whole-frame ratio from the ~1.06x that prompted issue #189 to 1.41x. A new per-ISA `hevc_color_convert` criterion group in `benches/hevc_decode.rs` times the stage under the same bit-exactness and per-site override guards as the other `hevc_*` groups, the `Stage::ColorConvert` profiler classification now counts as vectorized, and the breakdown in `benches/README.md` is re-measured with both arms reported side by side.

- Parse the AV1 frame header's `delta_q_params` bit and carry the specification's real coefficient CDF tables in both software decoders, so a non-lossless AV1 frame is read the way an independent decoder reads it. Three separate gaps sat between this crate and an interoperable non-lossless stream. First, §5.9.17 `delta_q_params` reads `delta_q_present` f(1) for *every* frame with `base_q_idx > 0`, gated on the quantizer alone and not on segmentation; neither `av1_intra_decoder` nor `av1_inter_decoder` read it, so every non-lossless frame header was one bit short from `delta_q_params` onward and each later field was shifted by one - which is why ffmpeg 7.1's dav1d rejects such a frame outright while still parsing the header (`zero_bit out of range: 1, but must be in [0,0]`) rather than mis-decoding it. Both decoders now read the bit, require it to be 0 (no per-block delta-Q is implemented, and §5.9.18 `delta_lf_params` is then absent entirely because it is gated on `delta_q_present`), and a lossless frame still reads no such bit, so existing lossless streams are unchanged bit-for-bit. Second, `av1_cdf` carried only the `qctx = 0`, `txSzCtx = 0` slice of `TXB_SKIP`, `COEFF_BASE`, `COEFF_BASE_EOB`, `COEFF_BR`, `DC_SIGN` and `EOB_EXTRA` - exactly what a lossless `TX_4X4`-only stream reaches and nothing more - while `EOB_PT_64`/`EOB_PT_256`/`EOB_PT_1024` and the `tx_depth` CDFs were invented approximations rather than the specification's defaults. All of these are now the specification's `Default_*_Cdf` tables carried in full, in a new `av1_cdf_tables` module, with their real quantizer-context dimension (`base_q_idx <= 20 / 60 / 120 / else`) and transform-size-context dimension; the decoders select the slice per frame and per transform instead of always using slice 0, and `tx_depth` selects the `Default_Tx_Size_Cdf` category its coding-block size calls for rather than one table for 8x8 and one for everything larger. Every `qctx = 0` / `TX_4X4` slice is pinned against the values the crate carried before, so no lossless stream changes meaning. Third, §8.3.2 `getTXBSkipCtx` returns context 0 outright when the transform covers the whole coding block, without consulting a neighbour; neither decoder implemented that case. It cannot fire on a lossless stream (transforms are all 4x4 while the partition reader never splits below an 8x8 coding block) but fires on nearly every block of a non-lossless one, and both decoders now implement it. The `ext_tx` CDFs are now the specification's `Default_Intra_Ext_Tx_Cdf`/`Default_Inter_Ext_Tx_Cdf` too, carried with their `txSzSqr` and intra-direction dimensions, so no invented probability model is left anywhere in `av1_cdf`. All three fixes land on the encoder as well as on both decoders, since a context or table that disagrees across them desynchronizes the round trip: `av1_encoder` writes `delta_q_present`, selects every coefficient CDF through the same shared accessors rather than through its own `qctx = 0`/`TX_4X4` copies (which are deleted, leaving one source of truth), and derives the same whole-block `getTXBSkipCtx`. ffmpeg 7.1 now parses a non-lossless frame header from this encoder instead of rejecting it, which `a_non_lossless_frame_header_is_accepted_by_independent_ffmpeg` pins. Its *tile* symbols are still not conformant - an independent reconstruction comes back at roughly 10-13 dB PSNR across every quantizer, frame size and content pattern measured, so at least one further context derivation disagrees with the specification - so that test asserts the header stage only and the encoder remains, as documented, a backend whose output is guaranteed interchangeable only in its lossless profile.
- Attribute HEVC decode time to stages, and settle where it actually goes. `cargo run --release --features native --example hevc_decode_profile` decodes the bundled 1080p sample through the ordinary public decoder with a new exclusive-time stage profiler running (`zvidlib::hevc_decode_profile`, instrumented on the decode path itself rather than behind a cargo feature, so what it measures is the build that ships) and prints each stage's share of the total, its share of decode proper, its per-frame cost and whether it reaches a vector kernel. Nested scopes are charged exclusively - the §7.3.8.11 residual parse is subtracted from the §7.3.8 slice-data walk it sits inside rather than counted in both - so the shares sum to the profiled total, and work in no scope is reported as its own `unattributed` row rather than spread across the stages. Profiling is off unless started, costs one thread-local flag read per scope when off, and is a no-op on `wasm32`, where there is no monotonic clock to attribute against. The measured breakdown, recorded in `benches/README.md`, contradicts the standing assumption that entropy decoding is why whole-frame SIMD reads flat: `slice_data_cabac` and `residual_cabac` are together 5.5% of the total and 8.2% of decode proper, while the already-vectorized stages cover 46.3% of the total and 69.6% of decode proper - an Amdahl ceiling of 1.86x that the observed ~1.06x falls well short of rather than being explained by. The largest single item is not decoding at all: the YUV420-to-RGBA `color_convert` pass every whole-frame measurement takes on the way out of the decoder is 33.5% of the total and has no vector kernel, so every whole-frame SIMD number is diluted by roughly a third for a stage no HEVC kernel touches. That, not CABAC, is the next target.
- Give the AV1 forward transforms a caller: `native_av1_video_encoder_factory` grows a non-lossless encode path, so `forward_transform` and its SSE4.1/AVX2/NEON kernels are now reachable from a real bitstream instead of only from tests and the benchmark. The profile is selected by the encoder's backend-private `configuration`, which was previously required to be empty and is now either empty (lossless, unchanged, still the default and still the only output verified against ffmpeg) or a single byte carrying the frame header's `base_q_idx`. A non-lossless frame signals `base_q_idx`, all-zero `loop_filter_params`, and `TX_MODE_SELECT`; each coding block chooses a square transform size through §5.11.16 `read_tx_size`, each transform block chooses a `tx_type` from the set §5.11.47 `get_tx_set` derives for it under `reduced_tx_set = 1` (`TX_SET_INTRA_2`, i.e. `IDTX`, `DCT_DCT`, `ADST_ADST`, `ADST_DCT`, and `DCT_ADST`, below 32x32, and `TX_SET_DCTONLY` from 32x32 up), so the forward ADST kernels are reachable too, and the quantized residual is coefficient-coded with the same §5.11.39 contexts the lossless path already derived, generalized from 4x4 to every square size. Forward quantization is the exact inverse of the `dc_q`/`ac_q` dequantization `av1_intra::inverse_transform` applies, and the encoder dequantizes and inverse-transforms every block it codes, so intra prediction runs off the same reconstruction the decoder builds rather than off the source. Transform size, transform type, and the partition split down to 16x16 are all chosen by minimizing `sse + lambda * bits`. On a 96x80 synthetic frame the encoder now spans roughly 52 dB at 4.8 KB (`base_q_idx = 1`) through 21 dB at 1.0 KB (`base_q_idx = 200`), against 6.3 KB for the lossless path, and a round-trip test asserts a distortion floor and a monotone quality-for-size trade at each step while covering every transform size and type the encoder can emit. The searches are exhaustive rather than early-terminated, so non-lossless encoding is currently tens of times slower than the lossless path (one 1920x1080 frame of the crate's synthetic test pattern took roughly 6.6 s at `base_q_idx = 32` against 0.15 s lossless, in the `dev` profile on an Apple Silicon host); lossless remains the default and is unaffected.
- Record the scope this leaves open: a non-lossless stream from this encoder round-trips through the crate's own AV1 decoder but is not yet interchange-grade. The symbols only a non-lossless frame reads (`eob_pt` above 16 coefficients, `tx_depth`, `ext_tx`) use this crate's placeholder CDFs rather than the specification's default tables, whose coefficient CDFs are additionally indexed by a quantizer context and a transform-size context this crate does not carry; the encoder also omits the `delta_q_present`/`delta_lf_present` bits and the `getTXBSkipCtx` whole-block special case, matching the decoder's parse rather than the specification. ffmpeg's dav1d rejects such a stream while still parsing the frame header (`zero_bit out of range`), which is the missing `delta_q_present` bit. Lossless output is byte-for-byte unchanged.
- Establish what the HEVC engine's x86_64 SSE4.1 and AVX2 kernels are actually worth, the half of #166 that #179 left open, and stop the SSE4.1 §8.5.3.3.4 weighted combine from being slower than the code it replaces. Measured on an AVX2-capable AMD x86_64 host with the two `#[ignore]`d stage benchmarks, each reporting the best of five interleaved rounds: two-dimensional 8-tap luma 2.1-2.3x (SSE4.1) and 2.4-2.7x (AVX2), two-dimensional 4-tap chroma 1.4x and 1.5x, `filter_taps` alone over an L1-resident buffer 1.1-1.3x and 2.5-2.7x, §8.7.3 SAO 4.6-4.8x and 6.3-6.7x, and §8.7.2 deblocking 1.3x on both - identical because a four-row edge segment is exactly one 4-lane vector, so the AVX2 path deliberately runs the same 128-bit kernel. The §8.5.3.3.4 combine was the one kernel behind, and it splits by vector width rather than by architecture: at SSE4.1's four lanes it measured 0.95x of scalar in the block path and level with it on a bare buffer - the same result #179 measured for the four-lane NEON kernel - because one or two multiply-accumulates, a shift and a clamp per sample is exactly what LLVM already vectorizes `combine_weighted_scalar` into under the crate's `lto = "fat"` / `codegen-units = 1` profile. `combine_weighted` therefore now dispatches to the scalar reference on SSE4.1 as it already did on NEON, and its SSE4.1 kernel is gone; the AVX2 kernel is kept and unchanged, since eight lanes is width the auto-vectorization does not reach and it measured 1.4x in the block path and 2.2x on a bare buffer. `filter_taps` keeps its kernels on both instruction sets. `bench_in_loop_filters` now reports one arm per instruction set the host offers rather than only the detected one, which is what makes a separate SSE4.1 reading obtainable on an AVX2 host, and asserts through `zvidlib::simd::active_by_site` that each pin actually reached the in-loop kernels, so a mis-routed override cannot be misread as a kernel that is not faster. The module's per-kernel table now covers x86_64 and aarch64 side by side instead of disclaiming that the x86_64 figures were never taken on x86_64 hardware. Every backend remains bit-exact with scalar and the existing equality tests are unchanged.
- Add the half-identity `V_*`/`H_*` inverse transform kernels, so every entry of every AV1 transform set is now decodable. `Tx1d` gains an `Identity` kernel and `Av1TxType` gains `V_DCT`, `H_DCT`, `V_ADST`, `H_ADST`, `V_FLIPADST` and `H_FLIPADST`; `inverse_transform` runs the identity along the axis the type names and the DCT or ADST butterfly along the other, with the flip where the type calls for one. Until now those types decoded correctly out of `get_tx_set`/`read_tx_type` but had no kernel and were rejected as `Unsupported`, which left `TX_SET_INTRA_1` (4x4/8x8 intra), `TX_SET_INTER_2` (16x16 inter) and especially `TX_SET_INTER_1` (4x4/8x8 inter, ten of whose sixteen entries were unimplemented) only partly decodable, so a conforming stream that picked one failed to decode. The identity pass carries AV1's own identity scale, `sqrt(N / 2)` in the same 14-bit fixed point the butterflies multiply in, because it shares a block with a butterfly pass whose gain it has to match - without it a half-identity block would reconstruct two to four times too small. The 2-D `IDTX` short path is unchanged and stays the unscaled pass-through it has always been, and only the ADST passes still fall back to the DCT above `TX_16X16`, since the identity is defined at every size. The encoder-side `forward_transform` applies the same scale, so a round trip through a half-identity type cancels exactly as it does for the others, and the SSE4.1/AVX2/NEON kernels cover the new types bit-exactly against the scalar path rather than falling back to it. New coverage decodes a bitstream signalling each new type - `V_DCT`/`H_DCT` from `TX_SET_INTRA_1` and `TX_SET_INTER_2`, and all sixteen `TX_SET_INTER_1` entries from an 8x8 inter transform block under `TX_MODE_SELECT` - and checks each reconstructs bit-exactly through the matching kernel and distinguishably from every other type. Decoded output for the checked-in AV1 elementary streams is unchanged: they signal no `tx_type` symbol.
- Select the AV1 luma deblocking filter length at the spec's transform-size thresholds. `av1_filters::filter_length_for_edge` required transforms twice as large as §7.14.5 does before each wide luma filter engaged - 16x16 for the 8-tap filter and 32x32 for the 14-tap - where the spec derives `filterSize` as `Min(16, Min(txDim, prevTxDim))` and §7.14.6 maps `4`/`8`/`>= 16` to `filter4`/`filter8`/`filter14`. An 8x8 transform edge that should take `filter8` was left on the narrow 4-tap filter and a 16x16 edge that should take `filter14` took `filter8`, so wide luma edges were under-smoothed relative to the reference decoder and luma disagreed with the chroma path, which already followed §7.14.5 exactly. Luma now takes the narrow filter at a perpendicular transform dimension of 4, the 8-tap filter at 8, and the 14-tap filter at 16 or more, with 32x32 and larger clamping to the same `filterSize` of 16 as 16x16 rather than being the only sizes that reach `filter14`. Decoded luma output changes for every edge in that range, and the selection is now checked against spec-derived vectors - a step edge deblocked end to end through `deblock_frame` at 8x8 and at 16x16 transform grids, compared against `Round2` sums computed from §7.14.6.3/§7.14.6.4's tap lists rather than from this crate's own tables - on every instruction set the host supports. The wide-filter weights themselves are unchanged.
- Add an encoder-side forward transform and quantization stage to the pure-Rust HEVC encoder (`src/hevc/engine/encoder/transform.rs`), the inverse of the decoder's §8.6.3 scaling and §8.6.4 transformation processes. `forward_transform` is the transpose of the §8.6.4.2 synthesis and covers the 4x4/8x8/16x16/32x32 DCT-II and the 4x4 DST-VII the intra luma path selects; `quantize` inverts the §8.6.3 scaling loop, applying `ScalingFactor` matrices as per-position reciprocals and deriving `qbits` from the same `bdShift` the decoder uses, so a forward-then-inverse pass reproduces its input to within one quantization step. `transform_and_quantize` runs both for a block, and `luma_qp` / `chroma_qp` derive the §8.6.1 quantization parameter (including Table 8-10) the two stages need. The transform reuses the decoder's vectorized butterfly by feeding it the transposed basis; quantization dispatches through a new AVX2 / SSE4.1 / NEON kernel registered as the `hevc_fwd_transform_quant` site in `zvidlib::simd::active_by_site`, so `zvidlib::simd::set_override` reaches it and every vector path is checked bit-exact against the scalar reference.
- Add a `hevc_encode_<size>_fwd_transform_quant` group to `cargo bench --bench hevc_encode`, run once per instruction set `zvidlib::simd::available()` reports, transforming and quantizing the whole picture at all four transform sizes per iteration. The target's `report_absent_stages` note no longer lists forward transform or quantization as unmeasurable; encoder-side reconstruction and in-loop filtering remain the stages the PCM bootstrap writer does not have.
- Decode the full AV1 transform-type signalling (spec §5.11.47 `get_tx_set`, §5.11.48 `read_tx_type`) in both the intra and inter software decoders, so the inverse ADST and flipped-ADST kernels are reachable from a bitstream instead of only through the public `inverse_transform` API. `reduced_tx_set` is now decoded rather than required to be 1, and a transform block selects `TX_SET_INTRA_1`/`TX_SET_INTRA_2` (intra) or `TX_SET_INTER_1`/`TX_SET_INTER_2`/`TX_SET_INTER_3` (inter) from its size, with `TX_SET_DCTONLY` above `TX_32X32` as before; intra blocks also select the `ext_tx` CDF by their `YMode`, as the specification does. A stream signalling `ADST_DCT`, `DCT_ADST`, `ADST_ADST`, `FLIPADST_DCT`, `DCT_FLIPADST`, `FLIPADST_FLIPADST`, `ADST_FLIPADST`, or `FLIPADST_ADST` now reconstructs through the matching kernel. The half-identity `V_*`/`H_*` types the larger sets also contain have no kernel in this crate and remain an explicit `Unsupported` error rather than being silently substituted, as does any ADST above `TX_16X16` (there is no 32-point ADST here). Decoded output for the checked-in AV1 elementary streams is unchanged: they signal no `tx_type` symbol.
- Record that zvidlib ships no audio encoder, and stop describing that as an open question. `AudioEncoder` is a contract with no implementation in the crate -- its only implementors are the pass-through PCM doubles in `tests/indexed_mp4_output.rs` and `benches/audio_mux.rs` -- and the README, `src/codec.rs`, `benches/audio_mux.rs`, and `benches/README.md` each previously left it undecided whether the crate would grow a native AAC-LC encoder, delegate to AudioToolbox/Media Foundation, or leave the trait to platform and browser backends. It leaves it to those backends, deliberately. A pure-Rust AAC-LC encoder is a filter bank, a psychoacoustic model, quantization and rate control, where the thing that has to be defended is output quality rather than throughput, and a mediocre encoder shipped under this crate's name is harder for a caller to route around than no encoder at all; every target already has a good one (`WebCodecs` `AudioEncoder` in browsers, AudioToolbox on macOS, Media Foundation on Windows), and delegating to any single platform encoder is per-platform work that leaves the other platforms uncovered. `MediaOutput` already muxes an audio track given any `AudioEncoder`, so the audio write path is complete up to the codec, which is the piece callers are best positioned to choose. Adding an implementation later stays additive and breaks no caller. The rationale now lives on the trait itself, with matching notes in the README and both benchmark documents.
- Benchmark the pure-Rust HEVC decoder per hot stage, not only end to end. `cargo bench --bench codec -- hevc_` now reports six per-stage criterion groups - §8.5.3.3 inter prediction, §8.4.4.2 intra prediction, §8.7.2 deblocking, §8.7.3 SAO, §8.6 dequantization plus inverse transform, and §9.3.4 CABAC bin decoding - each run once per instruction set the host supports, under the same bit-exactness and per-dispatch-site override guards the existing per-ISA groups use. Before this, a HEVC SIMD change could only be observed at the whole-frame level (`hevc_decode`, which needs the `ZVIDLIB_BENCH_LARGE=1` opt-in and the bundled 1080p sample), so a regression in one kernel was visible but not attributable; the stage groups need neither the opt-in nor the sample and say which kernel moved. CABAC is measured despite having no vector path and not being expected to grow one: the arithmetic decoder is inherently serial, so the fraction of a decode it owns is the Amdahl ceiling on what vectorizing everything else can buy, and that ceiling is only readable next to the other stages in the same report. The synthetic content deliberately mixes textured and flat regions because the wide deblocking filter is gated on the §8.7.2.5.3 flatness check - a purely textured plane would time only the narrow path and quietly under-report the kernel. The stage inputs come from a new narrow public surface, `zvidlib::hevc_decoder_bench`, over the otherwise crate-private HEVC engine, which is what lets an external benchmark crate reach the individual stages at all; its `HevcStageInputs::new` does every allocation and all content generation, so only the kernel under test runs inside a timed loop, and each stage returns an eight-byte fold over its full output rather than the output itself, keeping a multi-megabyte allocation out of the measurement while still failing the bit-exactness guard if any sample diverged. The two unverified performance claims in `Cargo.toml`'s profile comments now cite these benchmarks instead of a one-off measurement.
- Give the pure-Rust HEVC encoder an encode-side reconstruction path, and add the benchmark group that was blocked on it. Until now the encoder predicted from the *source* picture it was handed (`previous_y`), which is only correct while coding is lossless, and `src/hevc/engine/encoder/` had no counterpart to the decoder's `recon.rs`, `deblock.rs` or `sao.rs` at all. The new `engine/encoder/recon.rs` reconstructs every coded block the way a decoder will - form the prediction (from the previous reconstruction at the mode search's motion vector, or the neutral intra reference), code the residual against it, add it back and clip per §8.6.6 - and then runs the §8.7.2 deblocking filter and §8.7.3 SAO over the whole reconstructed picture through the decoder's own kernels, including the §8.7.2.5.4 / §8.7.3.1 PCM suppression map. The encoder keeps that reconstruction as its reference picture, so the RDO search in `rdo.rs` now predicts from what the decoder will hold rather than from what the caller passed in; the two are still identical sample for sample, because the shipped writer codes PCM losslessly with both loop filters neutralized (`pcm_loop_filter_disabled_flag == 1`), and keeping them separate is what makes that stay correct when it stops being true. The SAO stage is a real encoder-side parameter search, not a passthrough: per CTB and per component it picks the §8.7.3.2 edge-offset class whose per-category mean error against the source buys the largest SSE reduction, clamps each offset to the signalable range with the §7.4.9.3 inferred signs, and leaves the CTB off when no class buys anything. `benches/hevc_encode.rs` gains the `..._reconstruct` group (through a new `zvidlib::hevc_encoder_bench::plan_reconstruct` / `reconstruct_encoded_picture` pair that keeps the far more expensive mode search out of the timed loop), running at both benchmarked resolutions once per `simd::available()` instruction set under `bench_across_isas`, and `report_absent_stages` no longer lists reconstruction or in-loop filtering as missing - only the forward transform and quantization, which really do not exist yet. Measured on a heavily contended Apple Silicon host (best of repeated interleaved runs, so treat these as a floor): 640x352 reconstruction 11.2 ms scalar against 9.6 ms NEON, and the 1080p arms did not separate outside the host's noise. The in-loop filter kernels are vectorized, but they are a minority of this group's cost - the per-sample reconstruction loop and the SAO parameter search that precedes the filter are both scalar and dominate it - which is the measurement, and it names the next encoder-side vectorization target.
- Establish what the HEVC engine's aarch64 NEON kernels are actually worth, and stop the §8.5.3.3.4 weighted combine from being slower than the code it replaces. The two `#[ignore]`d stage benchmarks (`hevc::engine::inter_pred`'s `simd_inter_pred_benchmark` and `hevc::engine::simd::in_loop`'s `bench_in_loop_filters`) each timed one pass per backend, which on any machine doing other work swings by more than 2x - enough to report a real speedup as a regression, and the source of the "8-tap luma is 0.94x" reading that prompted this. Both now interleave the backends and report the best of five rounds, and the inter-prediction benchmark gains a second pair of arms that time `filter_taps` and `combine_weighted` alone over an L1-resident buffer, with the per-block `Vec` allocation the §8.5.3.3.3 block walk performs kept out of the measurement - that allocation is identical work on every backend and compresses every block-level ratio towards parity. Measured that way on an Apple Silicon host: two-dimensional 8-tap luma 1.6-1.7x, two-dimensional 4-tap chroma 1.54x, SAO 2.4x, §8.7.2 deblocking 1.3x, and `hevc_decode/neon` 1.0813 s against `hevc_decode/scalar` 1.1504 s (both ~15.9 Mpx/s) for the `hevc_decode/<isa>` arms. The §8.5.3.3.4 combine was the one kernel genuinely behind - 0.91x of scalar in the block path and 0.91x on a bare buffer - so `combine_weighted` now dispatches to the scalar reference on aarch64 and its NEON kernel is gone. That kernel is one or two multiply-accumulates, a shift and a clamp per sample, with no reduction or shuffle a hand-written version can express that the auto-vectorizer cannot; under the crate's `lto = "fat"` / `codegen-units = 1` profile LLVM already vectorizes the scalar loop to four-lane NEON and schedules it better. Widening the kernel to eight and sixteen samples per iteration, and dropping its redundant `#[target_feature(enable = "neon")]`, were both tried and measured slower still. `filter_taps` keeps its NEON kernel: at the 4..16-sample row lengths the block walk actually issues it is 1.6-1.9x scalar, even though it is level with scalar over one long buffer, and the module now documents what each kernel measured. Every backend remains bit-exact with scalar, with the equality tests extended to the lengths that straddle each vector step. x86_64 is unchanged - AVX2 has real width to add over a four-lane auto-vectorization - and untimed on x86_64 hardware, which is tracked separately.
- Add `cargo bench --bench av1_decode`, a criterion suite for the pure-Rust AV1 software decoder that measures whole-frame decode and every hot stage once per instruction set the host supports, and replace the ad-hoc `tests/av1_simd_bench.rs` with it. That file was an `#[ignore]`d integration test that hand-rolled its own timing loops and printed a table: useful input generators, no stored baselines, and nothing a regression could be tracked against.
