# Changelog

All notable changes to zvidlib will be documented in this file.

## Unreleased

- Establish what the encode-side §8.7.3 SAO band-offset search is worth vectorizing, the scalar half #276 left behind the edge-offset search #208 vectorized, and record where it is worth a kernel and where it is not. `band_stats` in `src/hevc/engine/encoder/recon.rs` walked every sample of every CTB of every plane inline; it now gathers a row at a time through a new `band_offset_row` dispatch site in `src/hevc/engine/encoder/recon_simd.rs`, so the band search is a named `hevc_recon` dispatch point like the edge search rather than a loop with no seam. That site dispatches to an SSE4.1 or AVX2 kernel on x86_64 and to the scalar reference on NEON, and both halves are measured results rather than omissions. The band search is a 32-way scatter, and none of the instruction sets this crate targets has one - masking 32 accumulators per vector costs far more than the four to eight dependent read-modify-writes it would replace, so all that is left to vectorize is the clamp, shift and widened subtraction in front of the scatter. Both shapes that leaves were written and measured on an Apple Silicon host against the scalar reference over L1-resident runs of 16 to 1024 samples, best of interleaved rounds, then measured again from a standalone harness to check the first: classifying into staging buffers and then scattering them read 0.42-1.30x, and classifying and scattering straight out of the vector lanes read 0.44-1.24x. Neither separates from scalar - both straddle 1.00x by less than the spread between repeats of the same measurement on this contended host, so those ranges are noise around parity rather than a win at any run length. The whole-picture `hevc_encode_640x352_reconstruct` group agreed, its NEON arm not improving. Neither kernel was landed, the same call `combine_weighted` got at four lanes. The site is kept rather than inlined so a future AVX-512 kernel, where `vpconflictd` and a real scatter change that arithmetic, has somewhere to go and a bit-exactness harness already pointed at it: the reference is asserted equal under every `simd::set_override` pin at every run length that straddles a vector step, and the whole-reconstruction equality test already covers the SAO decisions it feeds. On x86_64 the same classification does pay for itself, which the NEON measurement's analytical argument had been carried over to deny (issue #334). Timed across five CPU models - nine `ubuntu-latest` draws plus two `macos-15-intel` - best of nine interleaved rounds per draw and grouped by CPU model, because `ubuntu-latest` draws several models and they disagree by more than the effect: the same AVX2 arm read 1.10x, 1.45x and 0.97x on the first three draws purely because they landed on three different CPUs, while within a model the ratio reproduces to about +/-0.02 across independent draws. The lane-scatter shape reads 1.11-1.16x at 16 samples and 1.10-1.53x at 64 to 1024 on the Intel Xeon 6973P-C, Xeon Platinum 8573C, Core i7-8700B and AMD EPYC 7763; only AMD Zen 5 does not separate, and there it is a wash rather than a regression at the lengths this call sees, since a run is one CTB row of 16 to 64 samples and not the 1024 where it reads 0.97x. The AVX2 kernel is therefore dispatched to, with the SSE4.1 one - ahead of scalar on every model at every length, 1.02-1.45x - behind it for hosts without AVX2. AVX-512 was timed too, since `ubuntu-latest` turned out to draw AVX-512CD hosts and so the `vpconflictd` shape this entry pointed at was reachable, and neither AVX-512 shape landed: resolving the scatter's duplicate indices inside the vector unit reads 0.42-0.56x on every host that can run it, because the conflict-resolving pointer chase costs more than the read-modify-writes it removes at 32 bands over 16 lanes where duplicates are rare, and merely widening the classification to 512 bits reads 1.14-1.52x on the Intel parts but 0.21-0.30x on Zen 5, whose double-pumped AVX-512 makes the wider classification a large loss. No SAO decision, reconstructed picture or bitstream changes on any instruction set: the kernels accumulate in 32-bit lanes over runs no longer than one CTB row, so they are bit-exact against the scalar reference, which the existing per-instruction-set equality test asserts at every run length that straddles a vector step.

- Make an `av1_simd` kernel that has lost its instruction set to the inliner fail CI instead of waiting for someone to re-measure on x86_64. `#[target_feature]` widens the function it is written on and nothing that function calls, so the wrapper `simd_entry_points!` generates only widens the generic kernel it wraps for as long as LLVM keeps inlining that kernel into it. When the inliner declines, the kernel body is codegen'd at the target's *baseline* instruction set and every intrinsic in it becomes an out-of-line call through `core::core_arch` - the defect #336 measured and #337 repaired, which nothing enforced afterwards: the kernels stay bit-exact whether or not they keep the attribute, so no test fails and only a benchmark on an x86_64 host notices, and only if its ratio is read against scalar rather than against the previous run. `.github/scripts/check_simd_target_features.py` now enforces it from the emitted assembly rather than from the source: it builds the crate with `--emit=asm -C codegen-units=1 -C symbol-mangling-version=v0` and fails on either half of the defect's signature - a branch into `core::core_arch`, or a symbol for an `av1_simd` kernel monomorphized over one of the `av1_simd::vector` types, the kernel the wrapper was supposed to absorb left standing on its own. Removing `#[inline(always)]` from one entry point reproduces it: `deblock_edge_vertical::<Avx2>` reappears as a symbol, alongside 27 emitted intrinsics and the AVX2 wrapper branching into them. The first of those two rules is crate-wide and holds today with nothing to exempt, so it covers `hevc::engine::simd`, `hevc::engine::transform_simd`, `hevc::color_convert` and `av1_mc` too - an intrinsic emitted as a function is the same defect wherever it appears; the second is `av1_simd`-specific because only that module dispatches through generic kernels, the other sites writing their intrinsics directly inside the `#[target_feature]` function where there is no separate body to leave behind. The check runs in the `ubuntu-latest` Rust job and reports itself skipped elsewhere: on aarch64 NEON is in the baseline, so a kernel that lost its attribute still compiles to NEON and leaves no trace. Its parser is unit-tested from real symbols on every host through the existing `.github/scripts` suite, so the aarch64 runners still cover everything about it except the build it reads. No kernel's arithmetic changes and no output moves.

- Seeking into a long group of pictures no longer converts every frame it passes to RGBA, which was most of what the seek cost (issue #354). Reaching a frame means decoding every sample from the preceding random-access point, and each of those pictures went through the same full-resolution NV12-to-RGBA pass and 8 MiB allocation as the frame that was asked for, for nobody: on the bundled 1080p sample that pass is 6.6 ms against the 2.9 ms the decoding itself takes, measured through the `hevc_hardware_readback` seam, so two thirds of a seek was spent converting pictures nothing would draw - and the further along the timeline the seek landed, the more of them there were.

  `VideoDecoder` gains a defaulted `set_output_wanted`, which `ExactFrameReader` uses to tell the decoder that the pictures between where it is and where it was asked to be are wanted for reference only. VideoToolbox skips them with its own `kVTDecodeFrame_DoNotOutputFrame`; the software HEVC and AV1 decoders skip their colour conversion while still taking each picture through the reorder queue. Two kinds of frame are kept anyway, because the request after this one is very likely to be for them: anything at or after the target in *presentation* order, since a walk arrives from behind and carries on forwards - deciding this by decode position instead discards exactly the reordered frames a stream with B-pictures asks for next, which on the bundled sample made every fourth request reset the decoder and decode the group of pictures again - and the frames immediately behind the target, as many as the cache can hold. The second is what keeps a backward step free: a seek fills the cache with the frames just before where it lands, exactly as it did before, so nothing that used to be a cache hit becomes a decode. What is skipped is only what the cache would have evicted anyway. A frame that was skipped is not lost, only unreachable without a reset, and the reader tracks that as it already tracks a published frame it has evicted; a decoder that ignores the hint produces everything as before and the reader takes what it was handed rather than what it asked for. `DecodeStatistics` reports the skipped samples.

  On the bundled sample, through VideoToolbox: a cold seek to the last frame costs 1.5 s against 6.4 s, to the middle 0.9 s against 3.4 s, and a tenth of the way in 0.35 s against 0.66 s; stepping back past the frame cache from the end of the track 1.5 s against 6.4 s. Playing the track through is unchanged and skips nothing, since every frame in turn is a frame that was asked for. No decoded frame changes: `tests/codec_conformance.rs` and `tests/native_hevc_hardware.rs` check the frames a skipping walk stops on, the frames it passed, and the frames after it against the 768-frame fixture digests on the software and the hardware backend. NVDEC and Media Foundation implement the hint too (issue #358): each forwards it over the command channel its worker already uses, and skips the readback for a suppressed picture - the `cuvidMapVideoFrame`/`cuMemcpyDtoH`/unmap sequence on NVDEC, the D3D11 staging copy on Media Foundation, and the NV12-to-RGBA pass on both - while still decoding it as a reference and still consuming its presentation identity. Neither is measured or digest-checked: no host available to this repository has either backend, including CI, where `windows-latest` reports both as unavailable and every hardware test skips. The saving they should now get is the one VideoToolbox measured, and confirming it needs a host with the device.

  The native example's timeline drops its preview walk to use it. #319 and #339 had a drag stop on every frame between the decoder's position and the pointer and draw each one, so the picture would track the pointer - but with a single group of pictures every one of those stops is a frame from the *start* of the movie while the pointer is at the end, and each cost a conversion for a picture nowhere near where the pointer was. That is the "video frame freezes while it loads the next one" of #354. The worker now asks for the frame under the pointer and nothing else, and the window keeps the picture it has until that frame arrives: 1.7 s at the far end of the bar rather than 6.4 s, with the bar, the audio and the event loop as responsive as they already were. Committing a drag is still a cache hit, and so is stepping back a frame from where it landed.

- Derive the AV1 encoder's transform-gain calibration from measurements of its own rather than from the intersection of two assertions. `TYPE_GAIN_TRUST` and `TYPE_GAIN_MEMORY` had gone inert once #299 corrected the rate model - every frame of the tuning set read within 0.63% at every value of either knob - and what actually chose the pair was a 66-cell grid of which `(memory 1, trust 8)` was the only cell holding both the 0.05 dB distortion bound and the per-frame ceilings at once. Two measurements replace that. The tuning set now separates the *type gain*: every frame it had varied the residual energy across a region boundary, which is the axis the sampling interval's error lives on and not the one a shrinkage carries, so three `gain_*` frames put a sawtooth ramp or hard diagonal edges - content the `ADST` kernels win on - next to full-range noise, where they cannot, and the ratio genuinely changes across the boundary at every quantizer. And the last unmeasured assumption in the mechanism is now a constant with a sweep behind it: a trial that probed was corrected by the ratio it measured in full, not because anything measured that it should be but because the ratio was its own. It should not be. An estimator probing every size search, where every trial is corrected in full, reconstructs 0.344 dB *below* the exhaustive search at `qindex` 1 against the sampled estimator's +0.023 dB. `TYPE_GAIN_PROBE_TRUST` shrinks it to seven eighths, chosen where the tuning set's worst frame is lowest, and with it in force the 0.05 dB bound holds over a `13..=16` by `8..=10` region of the `(probe_trust, trust)` plane instead of at one point. The worst frame of the tuning set falls from +1.99% to +1.44%, `scene_edge`'s ceiling *tightens* from 2.5% to 1%, and no bound, ceiling or test was relaxed to get there. The residual 0.2 dB the DCT-only ranking carries at `qindex` 1 is measured to be none of these constants' to fix: probing *more* blocks makes it monotonically worse - -0.344 dB at two probes, -0.460 dB at six - while the candidate reduction falls under the 4x the bound requires, so a sharper estimate of the same ratio produces a worse size ranking. That is the extrapolation model, which assumes the type search's gain scales with a trial's searched cost and so over-credits the smallest size where every block is coded; replacing it is #349, and until then these are shrinkages against a model error rather than a sharper estimator. Two structural repairs were measured and rejected on the way, and both are on the record as sweeps: more probes, and removing the probing asymmetry altogether, which costs the tuning set's worst frame between +6.4% and +37.9%.

- Establish what an AV1 transform-size trial would have to reconstruct for its ranking to be the emitting pass's own, and record that it cannot be afforded. #299 corrected the rate model and #343 re-derived the calibration on top of it, and about 0.2 dB of size-ranking error survived both at `base_q_idx` 1; #349 crossed every shape of *credit* that could be given to a probe's measurement and moved not one size decision. The residual is in what a size trial **is**. A trial codes its blocks with the type set's `DCT_DCT` and probes a sample of them purely to measure - the block keeps DCT's result, so the trial's cost and coefficient contexts are a DCT-only trial's - while the emitting pass writes the type its own search picks and reconstructs from it. The two rank different encodes, and no scalar correction applied on top of a cost measured in the wrong contexts can reach that. The new `with_context_consistent_trials` removes the counterfactual and nothing else: every block of every size candidate runs the full type set and *keeps* the winner, with no correction afterwards. On the 96x80 `test_pattern` that reproduces the exhaustive search's size decisions **exactly** - all 37 coding blocks at `base_q_idx` 1 and every decision it makes at all six quantizers, to identical bytes and 0.000 dB, against the shipped estimator's 32 of 37 and the bare DCT-only ranking's 34 - so the counterfactual is the whole of the ranking error rather than part of it. It also cannot ship: it is the exhaustive type search run once per size candidate, buying a candidate reduction of 1.69x-1.93x on that frame where `the_search_shortcuts_stay_within_their_rate_and_distortion_bound` requires 4x, and across the tuning set at 128x96 it collapses to the whole exhaustive search (1.00x) on 30 of 48 frame-and-quantizer pairs and never exceeds 3.78x. `a_context_consistent_size_trial_ranks_like_the_exhaustive_search_and_costs_like_it` asserts both halves, the cost bound in the failing direction so that a future change which does bring it inside 4x is reported rather than missed. `TYPE_GAIN_TRUST` is therefore documented as what it is: a bias, permanently and by construction, damping a measurement of the wrong quantity because damping it costs less than believing it - not an estimator's shrinkage against noise - and it is to be re-derived by re-running `measure_type_gain_memory_against_trust`'s grid rather than reasoned about as a confidence. No shipped search, decision, reconstruction or bitstream changes, and no bound or ceiling was relaxed.

- CI now caches its Rust builds, and stops compiling `wasm-pack` from source to run four commands with it. Every job in `ci.yml` and `docs.yml` started from an empty `target/` and an empty cargo registry on every run, so each of the five of them rebuilt the whole dependency tree before it checked anything - and the `Benchmarks` job rebuilt it under `[profile.bench]`'s `lto = "fat"` and `codegen-units = 1`, which is the slowest build this repository has. Each job gains a `Swatinem/rust-cache` step keyed on the job, the runner, the toolchain and the manifest, so the fat-LTO artifacts and the ordinary ones never share an entry, and a failed run still stores the dependency build it got to. `cargo install wasm-pack --version 0.15.0 --locked` is replaced by the published musl binary of that same tag, which is a download rather than a build of a tool that is not this crate. Superseded pull-request runs are also cancelled now: the scarce resource is the runner pool, and a run for a commit that has already been pushed over queues ahead of one somebody is waiting on. `main` pushes and `workflow_dispatch` runs are never cancelled, because the benchmark baseline artifact is a chain and a cancelled link is a missing comparison for the run after it. `tests/ci_workflows_cache_cargo.rs` asserts every workflow job that invokes cargo carries the cache step, since a job that omits it is only slow, which is the one failure mode CI does not report on its own. No crate code changes, and no check was removed or weakened to make CI faster.
- Scrubbing an example's timeline is interactive rather than a multi-second freeze. #319 moved the native example's drag previews onto a worker thread, but everything else still decoded on the event loop: `PlaybackController::seek` only moves the clock, and the `current_frame` or `present` that follows it decodes forward from the preceding random-access point on whichever thread calls it. The bundled sample codes its 768 frames as a single group of pictures - its `stss` names exactly one sync sample - so committing a scrub decoded every frame from the start of the track on the thread that draws: 3.3 s a quarter of the way along the bar, 8.4 s at the end, against the 30 ms issue #333 asks for. Snapping a preview back to its random-access point, which #319 added to make previews cheap, had nothing to snap to on that sample either - every frame drawn during a drag was frame 0, so the picture never followed the pointer.

  `native_gl` now decodes every frame it draws on one worker thread, playback's included, and the event loop only ever collects what has arrived. The worker walks to the frame under the pointer from that frame's random-access point one frame at a time, publishing each one it passes, so the picture tracks a drag from the first intra picture onwards instead of holding still for the whole span; a newer pointer position redirects the walk, and one the current decode has already passed cancels it rather than being made to wait for a frame that will not be drawn. Playback reads through the same worker behind `PlaybackVideoSource`, so a frame that has not finished decoding is reported as the new `ErrorKind::WouldBlock` and the window keeps the picture it has and asks again on the next redraw - which is what lets playback resume immediately after a seek instead of stalling on the first `present`. Sharing the one reader is also what makes committing a drag free: the drag has already walked the decoder to the frame the commit asks for, so it is a cache hit rather than a second decode of the same hundreds of frames, and the example opens one decode session where it used to open two. On the bundled 1080p sample a scrub now costs the event-loop thread about 10 us and the picture follows within one 60 Hz redraw, against 3.3-8.4 s of frozen window before.

  `WasmVideoStream.get`'s `AbortSignal` now reaches inside the decode instead of only bracketing it. It was checked before and after the call, so a scrub that replaced a request left the decoder finishing the stale one - hundreds of frames of a single group of pictures - before the newest position could start. The signal is bridged to a `CancellationToken` the decode loop checks on every turn, so aborting frees the decoder part-way through. `web_canvas` uses it: a drag aborts the position it is replacing, and a target ahead of the frame on screen is walked to one frame at a time, drawing each, so the picture follows the pointer there too.

- Every AV1 SSE4.1 and AVX2 kernel that the x86_64 baseline recorded *below* the scalar reference was one the compiler had silently stripped of its instruction set, and they are all back above parity. `#[target_feature]` applies to the function it is written on and not to what that function calls, so a generic kernel body is only compiled with the feature enabled when it is inlined into the `#[target_feature]` wrapper `av1_simd`'s dispatch macro generates for it. The large kernels outgrew the inliner's size budget - the deblocking pair and all eleven transform drivers - and each wrapper degenerated into a tail call to a copy built at the target's *baseline* instruction set, where an intrinsic cannot be lowered inline and becomes an out-of-line call through `core::core_arch` with its operand spilled to the stack. `deblock_edge_vertical::<Avx2>` compiled to 961 such calls and not one AVX2 instruction. That is why the failure was x86_64-only and why AVX2 was so much worse than SSE4.1: NEON is in the aarch64 baseline and lowers inline either way, while on x86_64 the baseline is plain `x86-64`, so the SSE2-level operations still inlined and only the genuinely SSE4.1 ones (`pmulld`, `pminsd`, `pmovzxbd`, `packusdw`) became calls, against AVX2 where *every* operation did. Marking the fourteen kernel entry points `#[inline(always)]` - a correctness-of-codegen requirement here, not a speed hint, and documented as one at the dispatch macro - leaves no out-of-line `core_arch` call anywhere in the module. Measured on `ubuntu-latest`, before and after, `sse4.1`/`avx2` against each group's own scalar arm: `av1_deblock` 0.84x/0.24x to 6.73x/7.89x, `av1_deblock_wide` 0.62x/**0.13x** to 2.86x/3.08x, `av1_deblock_boundary` 0.91x/0.22x to 4.63x/4.34x, `av1_deblock_chroma` 0.79x/0.20x to 2.21x/2.37x, `av1_forward_dct_16x16` 0.25x/0.26x to 2.82x/3.06x, `av1_forward_dct_32x32` 0.26x/0.26x to 1.24x/1.55x, `av1_forward_flipadst_16x16` 0.20x/0.23x to 2.66x/2.92x, `av1_inverse_flipadst_16x16` 0.49x/0.49x to 1.44x/1.55x, `av1_inverse_adst_8x8` 0.69x/0.68x to 1.72x/1.43x. Two groups that were already above parity moved with them, because their drivers were outlined too: `av1_forward_dct_8x8` 0.86x to 3.31x/3.66x and `av1_forward_dct_4x4` 1.79x to 6.01x. At whole-frame level `av1_encode_frame_q32` goes 0.52x to 1.43x/1.52x and `av1_encode_frame_q160` 0.48x to 1.42x/1.49x, so an x86_64 user of the AV1 encoder stops paying roughly 2x for having a vector path and starts getting 1.4x back for it. Every kernel is unchanged line for line, `available_isas` still agree bit-for-bit at every pinned instruction set, and no decoded picture or emitted bitstream moves.

  Two rows in that table were not the inlining defect and are handled on their own terms. `av1_intra_smooth` read 0.47x/0.48x on x86_64 and 1.05x on `neon` for *identical arithmetic*: the §7.11.2.6 smooth predictor has no vector kernel, and its three per-instruction-set arms only forwarded to `smooth_row_scalar`. A `#[target_feature]` function can never be inlined into a caller that does not carry the feature, so on x86_64 those placeholders cost a call that could not be merged into the row loop, while on aarch64 the same wrapper adds no feature over the baseline and inlines away - which is the whole of the difference between the two hosts. The arms are removed and `smooth_row` calls the reference directly on every instruction set; a real kernel earns them back. `av1_encode_stage_wht` read 0.67x/0.69x before the repair and 0.67x/0.70x after it, so the forward 4x4 WHT is the one case where the vector form genuinely does not beat what LLVM produces from the scalar reference at `lto = "fat"` / `codegen-units = 1`. Its two passes are fourteen adds, subtracts and shifts of SSE2-baseline operations that LLVM already auto-vectorizes out of `av1_encoder::wht`, and what the kernel adds on top is three `transpose4`s - twenty-four shuffle micro-operations contending for one or two shuffle ports against a scalar loop with no shuffles at all. `av1_simd::fwht4x4` now returns `None` on x86_64 so the dispatch site falls back to that reference, with the reasoning recorded at the site, and the group reads at parity afterwards - 1.30x/1.24x at 320x180 and 1.23x/1.29x at 1080p, which is the same code under all three arms rather than a win. `neon`, where the shuffle issue width is what makes the kernel win 2.72x, keeps it. The whole set was re-confirmed on an AMD EPYC 9V74, the part the sub-parity table was drawn on: `av1_encode_frame_q32` 1.45x/1.54x and `av1_encode_frame_q160` 1.46x/1.54x there, against the 0.52x and 0.48x it recorded.
- Establish whether the calibrated SAO multiplier can price the §8.7.3 per-CTB search, the fixed 2.5x band-syntax charge #274 left in `band_offset_bins`, and record that it cannot. The charge is no longer a factor folded into a bin count: `band_offset_bins` is gone, `band_syntax_bins` in `src/hevc/engine/encoder/recon.rs` counts the five `sao_band_position` bins and the `sao_offset_sign` bins and nothing else, and what they cost is a price the search is handed, the new `SaoLambda`'s `band_q8`, beside the closed-form `mode_q8` every other bin is charged at. That separation is what let the question be measured rather than argued, and the QP 12-51 sweep on both test pictures at both sizes - `sao_sweep`, new and on the record - answers it three ways. Reading the price off the slice-level probe the way `calibrated_sao_lambda_q8` reads the slice-level multiplier lands at 1.1x-1.4x `lambda_q8`, whether the probe is read for its secant out to `sao_bits` or for the steepest thing it can give, the tangent at the picture's own coded point. Below 1.5x the writer accepts a band component at noise 128x96 QP 32 that puts the slice 0.003 dB under its own SAO-off curve, which is `every_accepted_sao_point_sits_on_the_writers_own_curve` failing. At `SAO_LAMBDA_BAND`, the trust bound, band offset is never selected at all and #274's operating points go with it. It drove a uniform grid of 16x16 bi-predicted *luma-only* blocks; the bundled sample's 48 frames reconstruct 89,213 prediction units over 100,156,544 luma samples that are 62.1% 64x64, 31.1% 32x32, 5.3% 16x16 and 1.4% 8x8 by sample, 38.4% of them uni-predicted, each luma sample bringing half a chroma sample through the §8.5.3.3.3.3 4-tap filter. That mix is now what the group runs, and a test pins it so a schedule that drifted back towards one size would read as a narrower workload rather than a faster kernel. It matters because the 8-tap kernel's margin over the auto-vectorized scalar reference is a function of block size and runs the opposite way to the ticket's assumption — 1.43x at 8x8, 1.25x at 16x16, 1.10x at 32x32, 1.04x at 64x64 — the same effect the `engine::simd` table already records as 1.6-1.9x in the block path against ~1.0x over one long L1-resident buffer, since a 64x64 two-dimensional 8-tap needs a 64x71 intermediate and is the buffer case in all but name. Sample-weighting that sweep predicts 1.07x for the real mix and the rebuilt group measures 1.09x, against the old grid's 1.25x on the same host on the same day; neither uni-prediction nor chroma moves it, so block size accounts for the whole difference. With both accounted for, the isolated group at 1.09x and the in-decode kernel arm at 1.07x agree: the two measurements were consistent and the expectation was wrong.

- Make the native AV1 encoder's serial range coder faster, which is the first change to move the lossless encode end to end. With the §8.3.2 coefficient contexts vectorized, a `sample` profile put 64% of `FrameEncoder::encode` inside `SymbolEncoder::encode_symbol` - and that is serial by construction in the same way the HEVC §9.3.5 CABAC encoder is, so it took the two serial changes the HEVC side had already measured wins from rather than another SIMD dispatch family. First, the bit sink: `src/av1_encoder/symbol.rs` followed `od_ec` in buffering every output byte as a `u16` so a pending carry could live in bit 8, then resolving all of them in a second reverse pass over the whole stream at `finish`. It now normalizes each byte as it arrives - a carry can only sweep the trailing run of `0xFF` bytes, which the encoder tracks, so the sweep is amortised constant time - which halves the sink and drops the pass entirely. Second, the literal-bit runs: coefficient signs, the `eob` extra bits and the exp-Golomb tails were each coded a bin at a time through the generic CDF path. `encode_literal` is now a specialization of the interval update for the one CDF `read_bool` ever uses, where both branches collapse onto the same split point, so a run keeps `low`, `rng` and `cnt` in registers across all of its bits instead of reloading them per bit; and the call sites hand it whole runs, the Golomb tail as a single field because `len - 1` zeros followed by `x` in `len` bits is just `x` written in `2 * len - 1` bits.

  Best of interleaved rounds per arm on an Apple Silicon host, `--release`, five rounds at 640x352 and seven at 1920x1080: `av1_encode_stage_symbol` 2.20 ms to 1.77 ms and 21.4 ms to 16.7 ms, `av1_encode_stage_tile` 36.5 ms to 33.0 ms and 400 ms to 310 ms, `av1_encode_frame_q0` 38.4 ms to 34.9 ms and 442 ms to 318 ms - 1.24x to 1.39x depending on the group and the size, and the whole-frame groups moving with the tile group for the first time. The encoded bitstream is byte-identical: every benchmark group's `bench_across_isas` guard reports the output byte count it reported before, and the encoder's `one_frame_encodes_identically_under_every_instruction_set` and `a_fixed_frame_encodes_to_the_same_bytes_on_every_host` digests are unchanged. The unrolled literal path is asserted byte-identical against the bit-at-a-time reference engine at every run length from 1 to 24 - exhaustively over every value up to 10 bits, sampled with the extremes above that - and again over a 50,000-event stream that interleaves runs with CDF-coded symbols, so the runs are entered at arbitrary coder state rather than only from a fresh encoder. The eager carry sink is asserted against a transcription of `od_ec_enc_done`'s reverse pass over adversarial digit sequences, including a carry sweeping 64 `0xFF` bytes and a carry off the front of the stream that both engines discard. `benches/README.md`'s "Why the tile group barely moves" gains a "What the serial work bought" section, so its 64% figure now reads as the state before this rather than the state now.

- Vectorize the HEVC encoder's lossy reconstruction path. The §8.6.6 add-and-clip of the encode-side reconstruction was only vectorized for the exact-residual (PCM) writer; the quantized residual writer - the path a real encode takes - still wrote back `Clip1(prediction + coded)` one sample at a time through `Picture::set_sample`. `src/hevc/engine/encoder/recon_simd.rs` gains an i32 add-and-clip kernel with SSE4.1, AVX2 and NEON backends dispatching through the existing `hevc_recon` site, and the quantized writer now reconstructs a whole transform-block row per call. The kernels stay in 32-bit lanes because a dequantized residual does not fit the 16-bit lanes the exact-residual kernel uses, so the result is bit-identical to the scalar reference on every instruction set: asserted directly against each backend over every run length that exercises a partial vector and a scalar tail, and end to end by a reconstruction that must come out byte-identical on every instruction set at every QP the round-trip tests cover. `benches/hevc_encode.rs` gains a `*_reconstruct_quantized` arm so the path is measurable, since the existing `*_reconstruct` arm only exercises the exact-residual path. That arm also caught a latent panic in the same writer: §7.3.8.8 transform blocks bottom out at 4x4, but the 4:2:0 chroma half of an asymmetric 16x4 or 16x12 partition measures 8x2 or 8x6 and is not a whole number of them, so the residual loop indexed past the end of the chroma plane on any picture whose mode search picked one. The cause was modelling the transform tree on the prediction partition; §7.3.8.8 hangs it off the coding unit instead, which is why a 16x16 coding unit keeps an 8x8 chroma transform block however its prediction is split. The residual round trip and the §8.6.6 write-back are therefore driven from the coding unit rather than from each partition — one 16x16 luma and two 8x8 chroma transform blocks per CU, tiling it exactly, so no block is ever clipped or zero-padded and none can reach past the end of a plane. The prediction geometry is still each partition's own, gathered into a coding-unit-sized buffer that the residual coding reads whole; a picture is now asserted to reconstruct identically under every partitioning that predicts the same samples, which is the property the per-partition tree did not have.

- Vectorize the native AV1 encoder's §8.3.2 `coeff_base` / `coeff_br` context derivation, the data-parallel half of the coefficient coding loop that `benches/av1_encode.rs` identified as the lossless encoder's remaining hot spot. `src/av1_simd/coeff.rs` is a new SSE4.1/AVX2/NEON dispatch family, registered as the `av1_coeff_ctx` site of `simd::active_by_site()` so `simd::set_override` pins it like every other kernel. It derives a whole transform block's contexts in one pass ahead of the serial symbol loop rather than one position at a time inside it, which is legal because both offset tables reach only down and to the right while the loop walks the up-right diagonal scan backwards - so every neighbour a position consults is already final, or zero past the end-of-block. The levels live in a zero-padded plane whose border is written once per block size, turning each neighbour into an unaligned load with no per-lane bounds branch. Every backend is a lane-by-lane transliteration of the scalar reference, so the encoded bitstream is byte-identical under every instruction set: asserted by the existing `bench_across_isas` guard, by unit tests over every width from 1 to 18 and at 32 and 64 - covering the partial trailing vector at both lane counts - and by a test that replays the incremental derivation the coding loop used to do, for every end-of-block a block can have.

  The measured result is that this was worth less than the issue expected, and the benchmarks now say so rather than leaving it to be re-derived. A new `av1_encode_stage_coeff_ctx` group measures the pass on its own and shows the kernel plainly - 3.05 ms scalar against 1.69 ms NEON at 640x352 on an Apple Silicon host, best of interleaved rounds, 1.8x - but `av1_encode_stage_tile` and `av1_encode_frame_q0` stay within run-to-run noise of their `main` numbers, because the pass is only about 9% of a tile encode. A `sample` profile says where the other 91% is: 9,164 of 14,411 samples inside `FrameEncoder::encode` are in `SymbolEncoder::encode_symbol`. What remains of coefficient coding once the contexts are vectorized is the range coder, which is serial by construction in the same way the HEVC CABAC encoder is, so the remaining AV1 lossless headroom is a serial question - a wider bit sink, unrolled literal-bit runs - and not another dispatch family. `benches/README.md` records that under "Why the tile group barely moves".

- Vectorize the two scalar stages that dominate the pure-Rust HEVC encoder's reconstruction pass, and register them as a SIMD dispatch site of their own. `benches/hevc_encode.rs`'s `..._reconstruct` group barely separated across instruction sets because the in-loop filter kernels it calls -- the decoder's, already vectorized -- are a minority of its cost: the §8.6.6 reconstruction loop in `src/hevc/engine/encoder/recon.rs` formed the prediction, differenced it against the source and clipped one sample at a time over every plane of every partition, and `class_offsets`, the encode-side §8.7.3 SAO parameter search, classified every sample of every CTB into a §8.7.3.2 edge category once per candidate edge-offset class -- four full scalar passes over the picture before the filter itself ran. Both now dispatch through a new `src/hevc/engine/encoder/recon_simd.rs` to SSE4.1 or AVX2 on `x86_64`, NEON on `aarch64`, or the portable scalar reference elsewhere, exactly as `rdcost.rs` already did for the distortion metrics. Reaching them needed the surrounding loops restructured, not just their bodies replaced: the prediction of a row is now gathered contiguously once, by both the exact-residual path the kernel then reconstructs whole and the quantized path that transforms it block by block (a plain copy whenever the motion vector keeps the row inside the reference, falling back to the per-sample §8.5.3.3.2 edge clamp only for a row that hangs off an edge) so the add-and-clip is a straight-line run, and the SAO search's per-sample neighbour bounds test is hoisted into a row range, since for a fixed edge-offset class "both neighbours are inside the plane" is a whole-row condition vertically and a contiguous run horizontally. The public `simd::active_by_site()` gains an entry of its own, `hevc_recon`, so `simd::set_override` is observably reaching these kernels and every benchmark group's override guard covers them. Both kernels are asserted bit-exact against the scalar reference on every instruction set the host supports, at every run length that exercises a full vector body, a partial one and the scalar tail, and the whole reconstruction -- including the SAO decisions it signals -- is asserted identical across every available instruction set for both an intra and an inter picture. Nothing about the encoder's output changes; only how fast a reference picture is reconstructed.
- The AV1 encoder's emitting pass no longer reads a transform-type search back from a size trial's probe. The reuse was added earlier in this same unreleased cycle and is measured out and withdrawn here; what remains of it is the shared reconstruct-and-code path the two searches were made to share, which is worth keeping on its own. What killed it is a ceiling rather than a tuning miss, and `measure_probe_reuse_coverage` is the measurement rather than the argument: on the 640x352 frame at `base_q_idx` 32 the emitting pass writes 1,870 transform blocks and only 44 of them run a transform-type search over more than one candidate at all, because the zero-block shortcut decides 1,716 of them outright and every 32x32 block's §5.11.48 reduced set names a single type. Reading a probe back could therefore never have spared more than those 44 blocks - 220 of the frame's 18,957 candidate evaluations, 1.2% - and at `base_q_idx` 160, where every emitted block is 32x32, the ceiling is zero of 220. The cache reached 21 of the 44. The rest of the gap is where the two key sets diverge, which the same measurement classifies: of the 898 distinct blocks probed at 32, 382 are at a position the winning partition emits at a *different* transform size and 495 at a position that is not the start of an emitted block at all, while not one is a prediction mismatch - a probe lands on the first searched block of every trial of every *candidate* coding block, and the emitting pass walks only the winning partition's blocks. Removing it costs the 105 candidate evaluations it was saving at 32 (0.6%, 18,852 back to 18,957) and none at 160, and no wall-clock change this host can resolve: from the minimum of eight interleaved rounds per arm over three sessions, 0.210 s with the reuse against 0.179 s without at 32 and 0.203 s against 0.182 s at 160 - where the two arms evaluate byte-identically the same 17,044 candidates and produce the same 29,005 bytes, so that 10% spread is the noise floor and not a cost either way. The emitted bitstream is unchanged, `a_fixed_frame_encodes_to_the_same_bytes_on_every_host` passing on its committed digests without regeneration, and `FrameEncoder::probed`, `without_probe_reuse` and the probe's whole-set winner are gone with it; a probe measures what the type search is worth at a size and nothing else, which is what it was for.

- The native HEVC encoder can now be given a target bitrate instead of a fixed quantizer, which is what puts its rate-distortion mode decision into production. `native_hevc_video_encoder_factory`'s backend-private configuration gains a third form beside the existing `[]` (lossless PCM) and `[qp]` (lossy at that `SliceQpY`): four big-endian bytes giving a nonzero target in bits a second, so `1_000_000_u32.to_be_bytes()` asks for a megabit a second. The lengths discriminate, and both existing forms are byte-identical to before, because a caller that names a QP is asking for a picture rather than a rate and a caller that configures nothing should not have its output change. `engine/encoder/ratecontrol.rs` is the new piece: a one-step per-picture QP feedback loop over the standard model that a quantizer step doubles the rate every six QP, so the budget the frame duration implies and the bits the *previous* picture actually cost decide the next picture's `SliceQpY`. The writer is intra-only and every access unit an IDR, so there is no frame-type hierarchy to allocate across and no propagation to model; the loop opens on the bits-per-pixel the budget implies, measured against this writer rather than assumed, and moves at most one full rate doubling a picture so a cut cannot slam the quantizer to a limit. It is all integer arithmetic, including the base-2 logarithm, because a QP that landed differently on a different host would make the bitstream unreproducible. The bitrate path codes through `ModeSearch::RateDistortion` — the decision from the previous release that charges each intra candidate for the residual bits it would code, worth 4 to 9 percent at the same QP — which nothing selected before, because saved bits are only worth saving when there is a rate to spend them under; the variant's dead-code exemption is gone with it. A stream settles within 25 percent of its per-picture budget, which is about as tight as an integer QP picked once a picture can promise, and decodes through `native_hevc_video_decoder_factory` like any other.
- Hardware HEVC decoding now reports what it spends on frame readback separately from the fixed-function decode. Every backend — NVDEC, Windows Media Foundation, and VideoToolbox — maps its own surface and converts it to RGBA inside `submit`, so a caller has only ever seen the two as one number, and for a playback pipeline the host round trip is often the part that bounds throughput. `zvidlib::hevc_hardware_readback` (internal and unstable, alongside `hevc_decoder_bench` and `hevc_decode_profile`) charges each delivered frame to two phases: the surface copy that makes the decoded surface CPU-readable — `cuvidMapVideoFrame` plus `cuMemcpyDtoH`, the staging-texture `CopySubresourceRegion` plus `Map`, or `CVPixelBufferLockBaseAddress` — and the NV12-to-RGBA pass over those bytes. `benches/hevc_hardware.rs` gains a `hevc_hardware_readback` group measuring each phase over the same 32-frame window `steady_state` uses, and prints both as ms/frame and as a share of the decode they are part of. The instrumentation is unconditional, two `Instant::now()` reads and a relaxed `fetch_add` per phase per frame, and its accumulators are process-wide atomics rather than thread-locals because NVDEC and VideoToolbox deliver frames from a callback that need not run on the submitting thread. The decoder's public output is unchanged: a zero-copy surface output path was considered and declined — three platform handle types and an NV12 output family whose contracts the crate does not own — with the reasoning recorded in `benches/README.md`.

- The native HEVC encoder's §8.7.3 SAO search now considers band offset (`SaoTypeIdx == 1`) alongside the four §8.7.3.2 edge-offset classes. `engine/encoder/recon.rs::estimate_sao` evaluates all 32 `sao_band_position` candidates per component — the four consecutive bands each taking their own mean error, clamped to the §7.4.9.3 signalable magnitude and signalled with a `sao_offset_sign` each — and scores them against the edge classes and against leaving SAO off under one `D + lambda * R` comparison, so the type is chosen by what it buys net of what it costs. Band offset's own syntax, the five position bins and its signs, is charged at 2.5x the closed-form multiplier, the coarse end of the departure the slice-level calibration measured, because it is rate that multiplier has never been checked against. The §7.4.9.3 chroma inference still holds: Cb and Cr share one type, each carrying its own offsets and, under band offset, its own `sao_band_position`. Band offset reaches the error edge offset cannot — a CTB biased over a *value range* rather than around a local edge — and the writer's §7.3.8.3 band path, previously never exercised, now reaches the bitstream. Measured over the QP 12–51 sweep on both test pictures against the same writer with SAO off: the noise-carrying picture at 64x48 QP 12 gains an operating point the edge-only search declined outright, +0.100 dB for +0.5% of slice, and at 128x96 five points it already took improve for one to eight bytes more — +0.120 dB at QP 12 against +0.106 before, +0.190 at QP 13, +0.167 at QP 14, +0.118 at QP 17 and +0.127 at QP 19. Every other point of the sweep is byte-identical, no point regresses, and every accepted point still sits on or above the SAO-off writer's own rate-distortion curve. Band offset is never selected on the smooth picture at any QP: that content's error is edge-shaped.
- Equal-cost transform and partition decisions in the AV1 encoder are now settled deliberately instead of by table order. The transform-type search compared candidates with a strict `<`, so a block whose best two types scored an identical `sse + lambda * bits` cost kept whichever one the derived transform set happened to list first - measured at exactly zero margin between `ADST_ADST` and `DCT_DCT` on a 4x4 block of the encoder's own test pattern, with a second block only four units away from a tie between `DCT_DCT` and `IDTX`. That was reproducible, but arbitrary: the winner was a property of a table's order rather than of the block, and any one-unit change to either cost silently flipped it. The type search now ranks on a total order over `(cost, symbol)`, breaking a tie towards the smaller `tx_type` symbol - the one the decoder reads earliest in the set and the cheaper of the two to signal - and the transform-size search breaks its own ties towards the largest transform, whose `read_tx_size` depth symbol is likewise the smallest. The partition search already preferred `PARTITION_NONE` on a tie, the cheaper side to signal, and now says so. Emitted bitstreams are unchanged: both tie-breaks were chosen to be the decision the previous candidate order already produced, so no committed digest moves. What changes is that the encoder no longer has a decision that only holds still because a table has not been reordered - the searches are now asserted to encode identically with their candidates evaluated backwards, and the ties that assertion depends on are asserted to actually occur.
- Re-take the HEVC engine's x86_64 SSE4.1 and AVX2 kernel ratios on an Intel host, so the `hevc::engine::simd` per-kernel table no longer speaks for x86_64 from one vendor's readings. The figures #215 recorded all came from an AMD EPYC-class `ubuntu-latest` runner; the same two `#[ignore]`d stage benchmarks have now been run on an Intel Coffee Lake host (`macos-15-intel`, i7-8700B, `sse4_1` + `avx2`, no AVX-512), three runs of best-of-five-interleaved-rounds each, against a same-day AMD control run so the two are compared on the same code. The question the ticket asked - whether the §8.5.3.3.4 `combine_weighted` SSE4.1 kernel, which measured 0.95x of scalar on Zen and is therefore dispatched to the scalar reference, lands on the other side of 1.00x on an Intel core whose `pmulld` behaves differently - is answered no: with the kernel temporarily restored so it could be timed, it read 1.00x in the block path and 0.75x over an L1-resident buffer on Coffee Lake, further below scalar than on Zen rather than above it. That dispatch is confirmed across both vendors and is unchanged, as is every other dispatch decision: no kernel changes which side of 1.00x it is on between the two. What does differ is magnitude, and the table now carries both vendors side by side rather than one: Intel reads materially lower on everything bounded by vector width (§8.7.3 SAO 2.7-3.0x against 4.6-7.4x, AVX2 `filter_taps` over a buffer 1.7-1.8x against 2.5-2.7x, two-dimensional 8-tap luma 1.6-1.9x against 2.1-2.7x) and slightly higher on §8.7.2 deblocking, which is bounded by edge shape instead. The one kernel whose *sign* is vendor-dependent is the AVX2 `combine_weighted`: 1.4x in the block path and 2.0-2.2x on a bare buffer on Zen, but 0.93-0.95x and 0.92-0.93x on Coffee Lake, where a 256-bit `vpmulld` is two uops against the four-lane `pmulld` LLVM auto-vectorizes the scalar loop into. It stays dispatched to unconditionally - the AMD win is large, the Intel cost is a few percent of one kernel, and splitting on a CPUID vendor check would add a second dispatch arm to keep bit-exact for it - and both the module table and the dispatch site now say so rather than leaving the AMD figure to stand for x86_64. No dispatch, kernel or decoded output changes; this is the measurement and what it is recorded against.
- Vectorize the HEVC decoder's 8-bit 4:2:0 YUV-to-RGBA output conversion, which was the largest single stage in a whole-frame decode and the only large one with no vector kernel at all. `picture_to_rgba` applied the fixed BT.601/709 limited-range integer matrix one sample at a time, and the issue #189 stage attribution measured it at a third of everything the whole-frame benchmark groups time - on the path of both `hevc_decode_1080p` and `hevc_decode/<isa>`, so every whole-frame SIMD number the suite reported was diluted by roughly a third for a stage no HEVC kernel touched. The conversion now lives in `src/hevc/color_convert.rs` with SSE4.1, AVX2 and NEON backends beside the scalar reference, dispatched through `zvidlib::simd` like every other kernel family in the crate: `simd::set_override` reaches it and `simd::active_by_site` reports it as `hevc_color_convert`. Each backend computes four (SSE4.1, NEON) or eight (AVX2) pixels at a time in `i32` lanes and writes each pixel's four components as one little-endian `R | G<<8 | B<<16 | 0xFF00_0000` word, so the RGBA interleave costs two shifts and two ORs rather than a byte-level pack, and each row's tail runs the scalar reference. Every backend is bit-exact with that reference - the arithmetic is `i32` throughout in the same order with the same arithmetic `>> 16`, a decoded 8-bit picture's samples are clipped to `0..=255` so no product can reach the scalar path's saturation, and a new test checks all of it across widths that leave a tail for both vector widths and across both chroma column parities. - `AacSampleReader::get_range` no longer throws away its decoded-packet cache every time a read advances. `ensure_decoded` treated `decoded` as all-or-nothing: any packet missing from the requested window reset the decoder, cleared the map, and re-decoded the window plus `preroll_packets`. Forward playback, which shares almost every packet with the read before it, therefore cost the same per request as a cold seek - about 100 us against about 1.5 us for a range already resident. The reader now tracks the contiguous run of packets the decoder has produced and, when a request starts inside that run or immediately after it, decodes only the access units past its end with no reset and no preroll; cold, backwards, and gapped requests keep the reset-plus-preroll path a real seek needs. Retained packets are bounded by the `Limits` knobs that already govern a decode - at most `max_decode_samples_per_seek` packets holding at most `max_allocation_bytes` of samples - with the packets furthest behind the request evicted first, and the per-read copy now visits only the buffers that overlap the request rather than the whole cache. Measured on an Apple Silicon host with the two bench binaries interleaved, `aac_reader_sequential/forward_walk_stereo_48k` goes from about 300 us to about 28 us per request, which takes a forward read from more expensive than a cold seek to roughly 3x cheaper than one, and `aac_reader_seek/random_seek_preroll_stereo_48k` does not regress. Decoded output is unchanged.

- The native HEVC encoder's lossy residual writer now runs the ITU-T H.265 §8.7.3 sample adaptive offset filter behind the §8.7.2 deblocking pass, in the §8.7.1 order. `engine/encoder/lossy.rs` emits `sample_adaptive_offset_enabled_flag == 1` in the SPS and the `slice_sao_luma_flag` / `slice_sao_chroma_flag` pair in the slice header, and codes the §7.3.8.3 `sao( )` structure per CTB — merge flags, `sao_type_idx`, `sao_offset_abs`, `sao_offset_sign`, `sao_band_position` and `sao_eo_class` — with the §9.3.3 binarizations and §9.3.4.2 contexts the decoder already parses. The parameters come from `engine/encoder/recon.rs::estimate_sao`, which was already there and unused by this writer; it now decides the two chroma components together on one shared class, because §7.4.9.3 infers `SaoTypeIdx[2]` and `SaoEoClass[2]` from cIdx 1 and a Cb and a Cr that picked different classes are not a bitstream. What `write_idr_residual_slice` returns is therefore still exactly what a conforming decoder reconstructs, sample for sample, at every QP, on both the smooth and the noise-carrying test picture.

  SAO is on, and the writer turns it off per slice when it does not pay. Unlike deblocking, which is signalled once in the PPS, SAO costs a `sao( )` structure on every CTB including every CTB it does nothing to, so the decision is taken twice. Per CTB a class is signalled only when the squared error it removes clears the bins it would be coded with, against the same closed-form `rdo::lambda_q8` the mode search uses — inside a picture already committed to the syntax, that is a choice between two codings of one CTB at one QP, which is the trade that multiplier is derived for. Per slice the whole pass is kept only when the error it actually removed clears the bits the whole grid actually costs, and that decision is taken against a multiplier measured off this picture's own rate-distortion curve rather than the closed form: the choice there is between spending bits on SAO and spending the same bits on a finer quantizer, so what the bits are worth is a property of the content, and the closed form misses this picture's own slope by 0.4x to 2.5x over the sweep. `curve_point` codes the same picture one QP finer, `calibrated_sao_lambda_q8` reads off the curve through those two points what the grid's bits are worth, and `keeps_sao` takes that probe only where its answer can still change the decision — outside the band the calibrated multiplier is clamped to, the closed form settles it alone, which over the sweep is half the pictures. When the pass is declined the reconstruction reverts to the deblocked one and both slice flags go out as 0, which §7.3.8.3 reads as "code nothing" and leaves the cost at the two header bits.

  Measured against the same writer with SAO off, at the same QP with the same mode decisions, in whole-picture PSNR and slice bytes over a QP 12 to 51 sweep on both test pictures at 64x48 and 128x96: the pass is taken at 36 of those points and buys +0.07 to +0.89 dB for +0.4% to +13.4% of the slice, including +0.73 dB for +11.4% on smooth content at QP 12 at 64x48 and +0.89 dB for +13.4% at 128x96. At every other point of the sweep the slice-level test declines it and the slice is the deblocked writer's to the byte, or within one byte of it. Every accepted point sits on or above the SAO-off writer's own rate-distortion curve, interpolated in log-rate at the same slice size — from +0.001 dB at the closest to +0.55 dB at the two clear wins. That is what the fixed multiplier could not do: it declined 30 of these points and accepted two others, the noise picture at QP 32, that sat 0.08 and 0.14 dB below that curve. The measurement costs the writer a second decision pass on the pictures where it is taken: the whole SAO stage is 19% to 25% of a picture's encode time where the band settles the decision without a probe, and 127% to 148% where it does not.

  The coding loop is now two passes over the picture rather than one, because §7.3.8.3 puts a CTB's SAO parameters at the head of that CTB's slice data while §8.7.1 only lets them be searched once the whole picture is coded and deblocked: a decision pass searches every coding unit and builds the reconstruction, the filters run, and a bitstream pass codes the recorded decisions with the `sao( )` syntax in front of each. Nothing a decision depends on changes in between — §8.4.4.2.2 intra prediction reads the unfiltered reconstruction, which the decision pass has already built — so the picture that is coded is exactly the picture that was searched, and no coding unit is searched twice.

The identity pass carries AV1's own identity scale, `sqrt(N / 2)` in the same 14-bit fixed point the butterflies multiply in, because it shares a block with a butterfly pass whose gain it has to match - without it a half-identity block would reconstruct two to four times too small.
